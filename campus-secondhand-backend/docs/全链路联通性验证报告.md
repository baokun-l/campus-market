### 2.6 买家可见性白名单（`statuses`）实测复核

> ⚠️ **本节结论已于 09-17 复验后修订。** 首轮结论「不给状态条件就返回全部，是刻意的后台语义」
> 只对**后台**成立；对**匿名**而言那是一条真实的数据泄露路径（详见 §5 的 P1-8 / P1-12）。
> 现已改为**服务端按访问者身份强制收敛**，白名单不再由调用方声明。下表为复验后的实测值。

**规则**（`GoodsService.fetchGoods`，与详情侧同口径）：

| 访问者 | 行为 |
|---|---|
| 后台角色（`admin`/`goods_admin`/`report_admin`） | 条件原样执行；不带条件 → 全量（含 `pending`/`off_shelf`） |
| 卖家查**自己的**发布（`sellerId` == 自己的 id） | 条件原样执行（「我的发布」要看得见待审/已下架） |
| 买家 / 匿名 | 只保留 `on_sale`/`sold`；条件被剔除干净时**退回默认范围**，不返回空页 |

实测（库内 16 件：`on_sale:13 pending:1 off_shelf:1 sold:1`）：

| 请求 | 身份 | total | 状态分布 | 结论 |
|---|---|---|---|---|
| 不带任何状态条件 | 匿名 | **14** | `on_sale:13 sold:1` | ✅ 不再返回全量 16 |
| 不带任何状态条件 | 后台 | 16 | 全 4 态 | ✅ 后台管理视图不受影响 |
| `statuses[]=on_sale&statuses[]=sold`（**axios 真实序列化格式**） | 匿名 | 14 | `on_sale:13 sold:1` | ✅ |
| `statuses%5B%5D=pending`（编码形态） | 匿名 | **14** | `on_sale:13 sold:1` | ✅ **越界条件被剔除，撑不开** |
| `status=pending` | 匿名 | **14** | `on_sale:13 sold:1` | ✅ 同上 |
| `statuses=pending,off_shelf` | 匿名 | **14** | `on_sale:13 sold:1` | ✅ 同上 |
| `statuses=pending` | 登录买家 | **14** | `on_sale:13 sold:1` | ✅ 登录也不放宽 |
| `sellerId=<他人>&statuses=pending` | 登录买家 | 4 | 该卖家的 `on_sale`（条件被剔除） | ✅ 传别人 id 不获得额外可见性 |
| `sellerId=<本人>&statuses=pending,off_shelf` | 该卖家 | ≥1 | 含 `pending` | ✅ **反向保障**：「我的发布」不受影响 |
| `statuses%5B%5D=pending` / `statuses=pending,off_shelf` | 后台 | ≥1 | 全为 `pending`(+`off_shelf`) | ✅ 后台精确筛选照常 |

前端四处调用方**均无需改动**（服务端收紧后，客户端继续传白名单是无害的冗余）：

| 视图 | 传入 | 含义 |
|---|---|---|
| `views/Home.vue` | `SELLABLE_STATUS` = `['on_sale']` | 首页推荐只推真正能买的 |
| `views/goods/List.vue` | `BUYER_VISIBLE_STATUS` = `['on_sale','sold']` | 广场可见「已售出」（有行情参考价值） |
| `views/user/PublicProfile.vue` | `sellerId` + `['on_sale','sold']` | 卖家主页「Ta 的在售」 |
| `views/admin/panels/GoodsPanel.vue` / `SettingsPanel.vue` | 不传状态 | 后台管理与 CSV 导出要全量（走后台角色分支） |

> **关键实现细节 1**：`GoodsController` 用 `Params.multiValue(request,"statuses")` **手动取值**，
> 而非 `@RequestParam List<String>`。因为 axios 会把数组序列化成 `statuses[]=on_sale`（带方括号），
> 按字面名绑定会**静默变成 null** —— 白名单一丢，审核中/已下架的商品就会直接出现在广场。
> 该处已按正确方式实现并实测通过（上表第 3 行）。

> **关键实现细节 2（写测试脚本时必踩）**：浏览器会自动把 `[` `]` 百分号编码成 `%5B%5D`，
> 而 **Node 的 `fetch` 走 WHATWG URL 解析并不会编码它们**。Tomcat 默认拒绝请求行中的原始 `[` `]`，
> 直接回 **HTTP 400 + HTML 错误页**（不是 JSON）。
> 因此用 Node 脚本测 `statuses[]` 时**必须自己写成 `%5B%5D`**，否则会得到一个纯属测试自身的假失败
> —— 本次复验最初那条唯一的 FAIL 就是这个原因，排查脚本见 `.workbuddy/probe-statuses.mjs`。

| 商品不存在 | `500` 商品不存在 | `404` 商品不存在 |
| 密码错误 | `500` 用户名或密码错误 | `1001` 用户名或密码错误 |
| 重复审核 | `500` | `1001` |
| 自购商品 | `500` | `1001` |
| 库存不足 | `500` | `1001` |
| 账号被封禁 | `500` | `403` |
| 公告不存在 | `500`「服务器内部错误」（原因丢失） | `404`「公告不存在」 |
| AI 不可用 | `500` + 等待 21 秒 | `200` code=0 模板文案 + **3 秒** |

> **为什么这件事重要**：`GlobalExceptionHandler` 会把 500 按 error 级记日志并提供通用文案。
> 修复前，一个用户输错密码就能在日志里造出「服务端异常」堆栈，真正的故障反而被淹没；
> 修复后 500 成为「真的出事了」的信号，日志可信度恢复。

**7. CORS 白名单只含 `5173` 与 `3000`**

**8. ⚠️ 非可售商品的**详情**可被匿名读取** → **✅ 已解决（09-17 复验）**

原状况：`statuses` 白名单只加在**列表**接口上，**详情接口没有对应判定** —— 广场挡住了，
但直接按 id 访问仍然读得到（匿名、不带 token，`GET /api/goods/12` 与 `/goods/6` 均返回 200 + 完整数据）。
影响是「审核中」的内容能被提前看到（详情链接一发出去，审核这道闸门就被绕过），
以及「已下架」的商品（含因违规下架的内容）仍可被任何人访问。

**修复**：`GoodsService.fetchGoodsDetail(id, viewerId, viewerRole)` 按「状态 + 当前身份」判定：

| 商品状态 | 可见人群 | 不可见时 |
|---|---|---|
| `on_sale` / `sold` | 任何人（含匿名） | — |
| `pending` / `off_shelf` | **卖家本人** 或 **后台角色**（`admin`/`goods_admin`/`report_admin`） | **404** |

**实测可见性矩阵**（`e2e-p1-8-orders.mjs` A / B 段，9 组组合全部符合预期）：

| 访问者 | `#12`(pending) | `#6`(off_shelf) | 依据 |
|---|---|---|---|
| 匿名 | **404** ✅ | **404** ✅ | 修复前是 200 |
| 卖家本人（`zhangsan` / `lisi`） | 200 ✅ | 200 ✅ | 「我的发布 → 查看」依赖这条 |
| 其他登录用户 | **404** ✅ | **404** ✅ | 不得提前看到他人待审内容 |
| `admin` / `goods_admin` / `report_admin` | 200 ✅ | 200 ✅ | 审核台与举报台要能复核 |

`on_sale` / `sold` 的匿名读取与浏览量累加**均未受影响**（1269 → 1270 ✅）。

> **一处需要修正的旧判断**：原报告说「需以可空方式取当前登录用户，不能直接依赖
> `AuthInterceptor` 注入的 `ATTR_USER_ID`」。实际核查后，`AuthInterceptor` 对**公开路径**也会

**10. ⚠️ 订单列表越权：不传 `role` 时返回全表订单（09-17 复验新发现）** → **✅ 已解决**

`OrderMapper.selectUserOrders` 原本只在 `role='buyer'` / `role='seller'` 时加过滤条件，
**其余情况 `WHERE 1=1`** —— 而前端 `fetchOrders` **恰恰不传 `role`**（它要的是「我和我相关的全部订单」）。

空表时完全看不出来；09-17 播种 9 笔订单后立刻现形：`zhangsan`（参与 5 笔）
拉到的却是**全部 9 笔**，其中包含完全无关的他人订单 —— **连收货地址一起返回**。

**修复**（`OrderMapper.xml` 用 `<choose>` 收口，已在 SQL 层强制，不依赖调用方传参）：

| 传入 `role` | 生成条件 |
|---|---|
| `buyer` | `buyer_id = 我` |
| `seller` | `seller_id = 我` |
| **不传 / 其他** | `(buyer_id = 我 OR seller_id = 我)` |

实测：`zhangsan` 5 笔（原本 9 笔）、`role=buyer` 3 笔、`role=seller` 2 笔、
**他人订单收货地址泄露数 = 0** ✅；管理员仍可检索全部 9 笔（后台订单管理不受影响）✅。

**11. ⚠️ 私信会话越权：非参与者可读取他人会话消息（09-17 复验新发现）** → **✅ 已解决**

`MessageMapper.selectBySession` 只按 `session_id` 过滤，**不校验归属**。
会话 id 规则是公开的（`s_{goodsId}_{min}_{max}`，商品与用户 id 都是明文可见的），
因此**只要猜出会话 id 就能读到别人的完整私聊记录**。

**修复**：加 `AND (from_user_id = #{userId} OR to_user_id = #{userId})`。
实测：`wangwu`（id=6）读 `s_15_4_5`（4↔5 的对话）→ **0 条** ✅，
而真正的参与者 `lisi` 读同一会话仍拿到 3 条 ✅；`wangwu` 自己的 4 个会话不受影响 ✅。

**12. ⚠️ 可见性白名单由调用方自己声明，等于没挡（09-17 复验新发现）** → **✅ 已解决**

买家侧之所以看不到「审核中 / 已下架」商品，靠的是**前端自己**传的 `statuses=[on_sale,sold]`。
但服务端对传入的状态条件**原样执行**，于是 `GET /api/goods?statuses=pending`（**匿名即可**）
就能把口子重新撑开，拿到 `pending` 商品的整个实体。这与 P1-8 是同一类缺陷，
只是路径从「按 id 读详情」换成了「按条件列列表」。

**修复**：见 §2.6 —— 可见范围改由服务端按身份判定，越界条件静默剔除后**退回默认范围**。
实测 5 组越界尝试（匿名 / 登录买家的 `statuses=pending`、`status=pending`、
`statuses=pending,off_shelf`、`sellerId=他人 + statuses=pending`）**越界条数全部为 0** ✅，
同时用**反向断言**锁住「卖家查自己仍能看见待审/已下架」，确保没有把「我的发布」改坏 ✅。

> 这三条（P1-10/11/12）有一个共同特征：**空表 + 前端不传参** 两个条件叠加时，
> 缺陷在功能测试里表现为「一切正常」。它们只有在**造了真实数据**并**按身份交叉验证**之后
> 才会暴露。这也是本轮把种子数据与可见性矩阵一起做掉的原因。

### 🟡 P2 — 可维护性与潜在陷阱

**8. `application.yml` 里的 `logic-delete-field: deleted` 是「死配置 + 潜在地雷」**

- 现状：`schema.sql` 里**没有任何 `deleted` 列**，实体类也没有 `deleted` 字段 → 该配置当前完全不生效（商品删除是物理删除）。
- 风险：一旦有人给实体加上 `deleted` 字段，MyBatis-Plus 会立刻开始生成 `WHERE deleted = 0`，
  而列不存在 → 所有查询直接 SQL 报错。**建议删掉这行，或补上对应列**，别让它悬着。

**9. 商品删除是物理删除，不可恢复**

`deleteGoods` 走 `deleteById`，且实体内无逻辑删除字段。对课程项目可接受，
但配合第 8 条一起看，删除策略是「配置说要逻辑删、实际在物理删」，语义不统一，建议明确二选一。

**10. 后端没有单元测试**

`src/test` 为空，构建时 surefire 直接 skip。本次验证靠的是外部 HTTP 脚本（见第六节），
但那些脚本不能替代回归测试。建议至少给 Service 层补几个测试（库存扣减、状态机、越权）。

**11. 两个后端端点前端未调用**

`GET /goods/{id}/detail`、`GET /orders/{id}/logs` 已实现但前端不调用（契约比对 MISSED=0 的另一面）。
保留无害，但会让契约比对每次都要人工确认这两行。

**12. `Result.error(String)` 仍是隐式 500 入口**

`BusinessException` 的单参默认码已修正，但 `Result.error(String)` 依然硬编码 `SERVER_ERROR`。
当前只被 `GlobalExceptionHandler` 和 `Result` 内部使用，**暂时没有外部误用**；
建议后续加一条静态检查（或直接删除这个重载），防止有人绕开异常体系又造出假 500。

**13. AI 功能在默认配置下是「模板降级」而非真 AI**

已确认 `api.openai.com` 在国内网络下**连接超时**（`ConnectException: Connection timed out`）。
现已降级为本地模板文案（3 秒返回，内容为平台真实规则），演示不会报错。
若要启用真实 AI：设置环境变量 `OPENAI_API_KEY` 与 `OPENAI_BASE_URL`（指向可访问的兼容端点）。
降级模板覆盖了退款/发货/审核/举报/支付五类常见问题。

**14. 响应头 `Content-Type` 未带 `charset=UTF-8`**

实测后端返回 `Content-Type: application/json`（无 charset）。

- **不影响浏览器与前端**：HTTP 规范中 `application/json` 的默认字符集就是 UTF-8，
  axios / fetch 解析中文完全正常（本轮已实测 `"categoryName":"运动"`、商品标题均正确）。
- **影响非浏览器客户端**：PowerShell 5.1 的 `Invoke-RestMethod` 会按系统 ANSI 解析，
  中文全部变成乱码 —— 本轮排查时实际撞上过一次，一度误判成后端编码问题。
  同理可能影响部分语言的 HTTP SDK 与手工 Postman 断言。

**建议**（低风险、纯收益）：给 Jackson 消息转换器显式设 UTF-8，
例如新增 `WebMvcConfigurer` 覆写 `extendMessageConverters`，
把 `MappingJackson2HttpMessageConverter` 的 `defaultCharset` 设为 `StandardCharsets.UTF_8`，
让响应头变成 `application/json;charset=UTF-8`。

**构建命令（照抄，可跑；09-17 复验实测 46s / BUILD SUCCESS / 零下载）**：

```bash
# ① 先停掉正在运行的后端（见下方坑 3），否则 repackage 一定会失败
"D:\apache-maven-3.9.4\bin\mvn.cmd" \
    -o -s <workspace>/.workbuddy/mvn-aliyun-settings.xml \
    -DskipTests package -f campus-secondhand-backend/pom.xml
```

**关于 Maven 的一个必知坑**：本机这两份 Maven 3.8.4 的 `conf/settings.xml` 都把 `localRepository`
指向 `C:\Program Files\Java\apache-maven\respository`，而该目录**无写权限**（Program Files 默认 ACL），
直接用会 `Access Denied`。而 **`-s` 不能自动躲开它** —— Maven 会把 global settings 与 `-s`
指定的 settings **合并**，global 那行仍然生效，**只有显式声明才会覆盖**。
因此 `.workbuddy/mvn-aliyun-settings.xml` 里已写明
`<localRepository>D:\apache-maven-3.9.4\mvn_repo</localRepository>`。
实测：Maven 3.8.4 构建 **26.9s，BUILD SUCCESS，零下载**（全部复用已有缓存）。

**三个环境级坑（非代码问题）**：

1. **沙箱会改写 `server.port`**。不传 `--server.port=8080` 时，Tomcat 会绑到一个被占用的随机端口并启动失败。
   启动后端一律显式加 `--server.port=8080`。
2. **安全删除护栏会拦截批量删除**。`vite build` 清空 `dist/`、Vite 重建依赖缓存时，
   会因「一次删除超过 50 个文件」被拦下报 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`。
   绕过方式：**先把目录重命名**（`mv dist .dist-old`），让 Vite 从零创建，而不是清空已有目录。
3. **重新打包前必须先停掉正在运行的后端**（09-17 复验新增）。Windows 上运行中的 JVM 会**锁住
   正在使用的 jar 文件**，`spring-boot-maven-plugin:repackage` 要把它重命名为 `.jar.original`
   就会失败，报的却是看起来毫不相关的：
   ```
   Unable to rename '...\campus-secondhand-backend-1.0.0.jar' to '...\jar.original'
   ```
   注意此时**编译本身是成功的**（日志里能看到 `Building jar:`），很容易被误判成 Maven 或权限问题。
   正确顺序：`停后端 → 构建 → 启后端`。本轮就踩过一次。
   顺带一提，`clean` 子目标在这个环境里也不稳（沙箱的批量删除护栏），
   实测用 `Remove-Item -Recurse -Force` 先删 `target/` 再 `package` 更顺。
