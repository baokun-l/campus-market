# 后端安全与健壮性体检报告

> 体检对象：`实践任务3：后端开发(前后端分离)/campus-secondhand-backend`
> 体检日期：2026-09-16
> 触发方式：对全部 9 个 Controller、9 个 Service、拦截器、全局异常处理、配置层做通读式复查
> 验证方式：`mvn clean package` **BUILD SUCCESS** + 接口契约脚本 **MISSING = 0**（前端 99 端点全覆盖）

---

## 一、总体结论

上一轮把「**接口契约**」补齐了（前端在调的 16 个接口后端都实现了）。
这一轮通读业务代码，发现的问题**全部落在契约之外** —— 也就是接口对得通、Mock 也过得去，
但**一旦切真实后端，就能被一条 curl 直接打穿**的那类问题。

| 等级 | 数量 | 性质 |
|---|---|---|
| **P0** | 3 | 可直接越权 / 提权，必须修 |
| **P1** | 4 | 数据完整性、权限撤销不干净 |
| **P2** | 4 | 健壮性、信息泄露、可运维性 |

**一句话**：三段式主流程（下单 → 支付 → 发货 → 收货 → 评价）是对的，
但**「谁能调这个接口」这一层基本是空的** —— 接口按契约接通了，权限却没跟上。

## 二、P0（越权 / 提权）

### P0-1　后台接口只验「登录」不验「角色」——任意学生可接管他人账号

- **位置**：`interceptor/AuthInterceptor.java`、`config/WebMvcConfig.java`
- **现象**：拦截器只判断「token 有效」，对 `/admin/**` 没有任何角色判定。
  前端的 `meta.requireAdmin` / `meta.roles` **只是路由守卫**，绕过页面直接打接口即失效。
- **影响**（任何已登录学生一条 curl 即可）：

  | 接口 | 后果 |
  |---|---|
  | `POST /admin/users/{id}/reset-password` | 把任意用户密码重置为 `123456` → **账号接管** |
  | `POST /admin/users/{id}/ban` | 封禁任何人 |
  | `PATCH /admin/settings` | 改平台配置（含补贴/费率口径） |
  | `DELETE /admin/audit-logs` | **抹掉审计痕迹**，事后不可追 |
  | `POST /admin/goods/batch-delete` | 批量删除全站商品 |
  | `POST /admin/orders/{id}/refund` | 伪造退款 |

- **修复**：拦截器内新增角色分区，口径与前端 `router/index.ts` 的 `meta` **逐条对齐**：

  | 路径 | 允许角色 |
  |---|---|
  | `/review/goods/**` | `admin`、`goods_admin`（商品审核后台） |
  | `/admin/reports/**` | `admin`、`report_admin`（举报处理后台） |
  | 其余 `/admin/**` | 仅 `admin` |

  判定顺序必须是「先审核子域、后 `/admin/**` 兜底」——
  顺序反了 `report_admin` 会被自己的后台挡在门外（`/admin/reports/**` 同样命中 `/admin/**`）。
  两个审核后台保持前端注释里的「职能互斥」：`goods_admin` 进不了举报域，反之亦然。

### P0-2　`DELETE /goods/{id}` 与 `PATCH /goods/{id}/status` 无归属校验

- **位置**：`controller/GoodsController.java`、`service/GoodsService.java`
- **现象**：`GoodsService` 里**已经写好**了带归属校验的重载（`requireOwner`），
  但 Controller 调的是**不带 operatorId 的那个重载**，校验形同虚设。
- **影响**：任意登录用户改个 id 就能**下架、删除他人商品**。
- **修复**：Controller 接上 `currentUserId` / `currentRole` 传下去；
  `requireOwner` 增加角色参数 —— `admin` / `goods_admin` 视为后台操作放行，其余必须是商品卖家本人。
  同时把「不带 operatorId」的重载标注为**仅供系统内部联动**，并加警示注释，防止再被 Controller 误用。

### P0-3　`POST /reviews` 完全采信请求体，可伪造评价

- **位置**：`controller/ContentController.java`、`service/ContentService.java`
- **现象**：`orderId` / `goodsId` / `toUserId` 全部取自请求体，且不校验评价人与该订单的关系。
- **影响**：拿别人的订单号刷评价；把 `toUserId` 填成任意用户给他**刷差评**
  （评价星级会进信誉分口径）；`rating` 传 null 时 `Math.max(1, null)` 拆箱 **NPE → 500**。
- **修复**：改为**以订单为准**——
  1. 订单必须存在，当前用户必须是该单的买家或卖家，否则 403；
  2. `goodsId` 忽略请求体，取订单上的值；
  3. `toUserId` 由订单推导（对方当事人），**不再采信客户端**；
  4. 订单状态必须是 `completed`；
  5. `rating` 为 null 时兜底为 5，`content` 空串拒绝。

## 三、P1（数据完整性 / 权限撤销）

### P1-1　封禁与降权「撤不干净」——旧 token 仍然全权可用

- **位置**：`interceptor/AuthInterceptor.java`
- **现象**：角色与状态全部取自 JWT 里的快照。JWT 一旦签发，服务端就改不动它。
  - 管理员封禁某人 → 对方**手上已有的 token 到期前照样畅通**（登录接口只拦「新登录」）；
  - 管理员把某人从 `admin` 降权 → 旧 token 里 `role` 还是 `admin`，后台照进。
- **修复**：已登录请求**回查一次 `t_user`**，用库里的 `status` / `role` 覆盖 Token 快照。
  封禁 / 账号不存在 → 回 `401`（业务码），前端会弹「登录状态已过期」并清 token 跳登录页，
  正是被踢下线应有的表现。代价是每请求一次主键查询，该项目体量可接受。

### P1-2　`POST /orders/{id}/review/append` 任何人可替别人追评

- **位置**：`controller/ContentController.java`、`service/ContentService.java`
- **现象**：`appendReview(orderId, content)` **没有发起人参数**。
- **修复**：签名加 `userId` / `role`，只有原评价人本人（或后台）能追评，空内容拒绝。

### P1-3　可以购买自己发布的商品

- **位置**：`service/OrderService.java`
- **现象**：无自购闸门，且**前端商品详情页也没有隐藏自己的「立即购买」**。
- **影响**：`buyerId == sellerId` 的订单会让「买家确认收货」「卖家发货」两套越权判定**同时成立**，
  并且自买自卖能把 **GMV 直接刷上去**。
- **修复**：`createOrder` 增加自购拦截（`不能购买自己发布的商品`）。
  ⚠️ **这是一个行为变更**：以前点自己的「立即购买」会成功，现在会明确报错。

### P1-4　库存扣减非原子，并发下超卖

- **位置**：`service/OrderService.java`
- **现象**：`selectById` 读出来 → 内存里减 → `updateById` 整体回写。
  两人同时抢最后一单，读到的 `stock` 都是 1、各自减成 0 再回写 → **两笔订单共用同一件库存**。
- **修复**：改为条件原子扣减 `update ... set stock = stock - qty where id = ? and stock >= qty`，
  受影响行数为 0 即库存不足；「售罄置 `sold`」放到扣减后重读再判，
  避免在同一条 SQL 里拼 `IF()` 这种方言写法。老数据 `stock` 列为 NULL 时保留原有宽松语义。

## 四、P2（健壮性 / 信息泄露）

### P2-1　认证失败返回 HTTP 401/403，导致前端两条分支永远走不到

- **现象**：后端**所有业务错误**都是「HTTP 200 + body 里的 code」（见 `GlobalExceptionHandler`），
  而拦截器却直接写 HTTP 401 / 403。
  axios 默认把非 2xx 丢进 **error 分支**，而 error 分支只认 404 / ≥500 / 网络错误，
  其余统一弹 `err.message` —— 也就是「`Request failed with status code 401`」这种英文乱码。
- **影响**：前端精心写好的两条分支成为死代码：

  | 前端设计 | 实际表现 |
  |---|---|
  | `code === 401` → 弹「登录状态已过期」+ logout + 跳 `/login` | 弹英文乱码，**不清 token、不跳登录** |
  | `code === 403` → 弹「您没有该操作权限」 | 弹英文乱码 |

  注意这是**修认证层之前就存在的隐藏问题**（token 过期从未真正触发过重新登录）。
- **修复**：拦截器改为 **HTTP 200 + body 业务码**，与全局异常处理的约定统一。
  认证层不该另搞一套状态码体系。

### P2-2　兜底异常把内部细节直吐前端

- **位置**：`common/GlobalExceptionHandler.java`
- **现象**：`handleOther` 直接 `Result.error(SERVER_ERROR, e.getMessage())`，
  等于把 SQL 片段、表名、NPE 的类名行号这类内部信息返回给调用方。
- **修复**：改为「**日志记全量、响应给通用文案**」（`服务器内部错误，请稍后再试`）。

### P2-3　参数错误被当成 500

- **现象**：`GET /orders/abc/logs`（路径变量类型不符）、请求体不是合法 JSON，
  原先都会落到兜底分支变成 **500「服务器异常」**，让人误判为后端挂了。
- **修复**：新增 `MethodArgumentTypeMismatchException`（→ 1001）、
  `HttpMessageNotReadableException`（→ 1001）、`NoResourceFoundException`（→ 404）三个处理器。

### P2-4　密码明文存储 + 凭据硬编码

- **现象 a（明文口令）**：`t_user.password` 存明文，登录直接 `equals` 比较；
  种子账号 `admin/admin123` 写死在 `schema.sql`。任何能看到库的人立刻拿到全部可用口令。
- **现象 b（凭据入库）**：数据库口令 `123456`、JWT 密钥明文写在 `application.yml`。
  JWT 密钥泄露 = 任何人可自签一个 `role=admin` 的 token 直接进后台。
- **修复 a**：接入 **BCrypt**（`spring-security-crypto`，只取算法本体，**不引入 Spring Security 过滤器链**，
  以免接管现有 JWT 路由规则）。采用**双模式兼容**：

  | 库里存的形式 | 校验方式 |
  |---|---|
  | `$2a$/$2b$/$2y$` 开头 | BCrypt 校验 |
  | 历史明文 | 按明文比对，**校验通过后顺手升级为哈希** |

  这样新注册 / 重置密码入库即为哈希；老账号**登录一次自动收敛**，无需手工迁移；
  `schema.sql` 的种子账号 `admin/admin123` **依然能直接登录，演示流程零改动**。
- **修复 b**：数据源与 JWT 全部改为 `${ENV:默认值}`，本机零配置可跑，换机器用环境变量覆盖。
- 顺带修掉：`user.getPassword().equals(password)` 在 `password` 列为空时会 **NPE → 500**。
