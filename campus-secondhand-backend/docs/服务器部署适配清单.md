## 1. 配置管理与环境变量

### P0-1　新增 `prod` profile，把生产配置收口到一个文件

- **现状**：`src/main/resources/` 下只有 `application.yml` 与 `application-demo.yml`，
  **没有 `application-prod.yml`**。生产环境完全依赖一堆环境变量裸奔。
- **改法**：新增 `application-prod.yml`（**文件内不含任何凭据，只写生产该变的默认值**）：

```yaml
# application-prod.yml —— 不含任何凭据；凭据一律走环境变量
server:
  forward-headers-strategy: framework        # 见 P0-4
logging:
  level:
    com.campus.market.mapper: info           # 见 P1-2
spring:
  sql:
    init:
      mode: never                            # 见 P1-5
jwt:
  secret: ${JWT_SECRET}                      # 无默认值 → 缺失直接启动失败，见 P0-3
cors:
  allowed-origins: ${CORS_ALLOWED_ORIGINS}
```

- **原因**：现在"生产要改哪些配置"这件事**只存在于人的记忆里**，没有任何文件可对照。
  漏一个就是事故，而且事后无法 review。收口之后，`git diff application-prod.yml` 就是生产配置的全部差异。

### P0-2　`demo` profile 绝不允许在生产出现

- **现状**：`application-demo.yml` 是**重置型**演示数据 —— `db/demo-data.sql` 会重建商品表
  （16 商品），`db/demo-data-orders.sql` 会**按主键删除固定 9 笔订单**。
- **改法**（三层，至少做前两层）—— **三层现已全部落地**：
  1. ✅ **部署脚本只允许 prod**：`deploy/campus-market.service` 把
     `--spring.profiles.active=prod` 写死在 `ExecStart` 里，不接受外部传参；
  2. ✅ **打包物理剔除 demo 资源**：`pom.xml` 新增 `prod` profile，
     用 `./mvnw -Pprod package` 时把 `application-demo.yml` 与 `db/demo-*.sql` 排除出 jar。
     实测（`.workbuddy/jar-entries.mjs` 解 jar 中央目录）：
     默认包 **7 条** demo 条目，`-Pprod` 包只剩 **1 条**（`DemoPayChannel.class`，正经的支付渠道类）。
     ★ 为什么这层值得单独做：前两层里第 1、3 层都是**运行时**判断，总有绕过的可能
     （手敲 `java -jar` 忘了写 profile、或临时用环境变量覆盖）；第 2 层是**编译期**的 ——
     资源根本不在包里，想跑也没有脚本可跑；
  3. ✅ **启动自检**：`DeploymentGuard`（`EnvironmentPostProcessor`）在连数据库之前拒绝带 `demo` 的启动
     （与清单原文略有差异：这里**没有**加"数据源不是 localhost"这个条件 ——
     判据不该是"库在哪台机器"，而是"这次启动会不会重置数据"。
     本地连本地库同样会清空真实数据，所以一律要求显式确认开关）。
- **原因**：这是全项目**唯一一个"参数写错就毁数据"的开关**。
  `schema-auto.sql` 是 `IF NOT EXISTS` 幂等的，很安全；但 demo 脚本不是。
  历史上项目已经因为一条 `LIKE '2026%'` 误删过 4 笔真实订单 —— 同类风险必须用机制而不是靠细心来防。

### P0-3　`JWT_SECRET` 在生产必须有值，且缺失即启动失败

- **现状**：`application.yml:163` `${JWT_SECRET:campus-secondhand-market-jwt-secret-key-2024}`；
  `JwtConfig.java:30` 把这个兜底值定义为常量，`@PostConstruct` 只 `log.warn` **并不阻断启动**。
- **改法**：`application-prod.yml` 里写成 `${JWT_SECRET}`（**去掉冒号后面的默认值**）→
  环境变量缺失时 Spring 直接抛 `IllegalArgumentException` 启动失败。
- **原因**：兜底密钥写在开源仓库里 = 公开。任何人拿它就能自签一个 `role=admin` 的 token 进后台
  （`AuthInterceptor` 只校验签名 + 回查 status/role，签名过了就直接放行）。
  只 warn 不 fail 的问题在于：**告警是会被忽略的**，而"启动失败"不会。
  当前设计对本地开发零配置是优点，对生产是缺口 —— 这正是 profile 该干的事。
- **同时**：密钥至少 32 字节随机串，生成方式 `openssl rand -base64 48`。

### P0-4　Nginx 反向代理必须配 `forward-headers-strategy`

- **现状**：未设置该参数。
- **改法**：`server.forward-headers-strategy: framework`；Nginx 侧传 `X-Forwarded-For` / `X-Forwarded-Proto`：
  ```nginx
  proxy_set_header Host              $host;
  proxy_set_header X-Real-IP         $remote_addr;
  proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
  ```
- **原因**：不配的话，Spring 认为自己是 HTTP、客户端 IP 是 Nginx 的 IP。
  当前代码没有依赖真实 IP，但**将来一加访问日志或限流（P1-5）就会全部记到 Nginx 那一个 IP 上**，
  表现为"限流把所有人一起限了"。现在配是零成本，事后补要重新过一遍日志。

### P1-1　数据源 URL 的三个参数在生产要改

- **现状**：`application.yml:46`
  ```
  useSSL=false & allowPublicKeyRetrieval=true & createDatabaseIfNotExist=true
  ```
- **改法**：生产 URL 改为
  ```
  jdbc:mysql://<host>:3306/campus_market?useUnicode=true&characterEncoding=utf-8
    &sslMode=REQUIRED&serverTimezone=Asia/Shanghai
    &connectionTimeZone=Asia/Shanghai&forceConnectionTimeZoneToSession=true
  ```
  即**去掉 `createDatabaseIfNotExist`**、**`sslMode=REQUIRED`**、补时区参数（时区见 P0-5）。
- **原因**：
  - `createDatabaseIfNotExist=true` 要求应用账号具备 **CREATE 权限**，而生产账号不该有；
  - `useSSL=false` 让应用到 DB 的流量（含库口令、用户手机号）明文过网；
  - `allowPublicKeyRetrieval=true` 在开启 SSL 后不再需要，留着是多余攻击面。

### P1-2　生产用独立低权限数据库账号，不用 `root`

- **现状**：`application.yml:47` `${DB_USERNAME:root}`。
- **改法**：
  ```sql
  CREATE USER 'campus_app'@'%' IDENTIFIED BY '<强口令>';
  GRANT SELECT, INSERT, UPDATE, DELETE ON campus_market.* TO 'campus_app'@'%';
  FLUSH PRIVILEGES;
  ```
- **原因**：`root` 一旦被通过应用层缺口利用（如某个未过滤的注入点），后果是**整个 MySQL 实例**，
  而不只是这一个库。只给 CRUD 的话，最坏情况被限制在单个库的数据面。

### P2-1　`cors.allowed-origins` 生产必须换成真实域名

- **现状**：`application.yml:171` 只有 `http://localhost:*`、`http://127.0.0.1:*`、`http://localhost:3000`。
- **改法**：环境变量 `CORS_ALLOWED_ORIGINS=https://your-domain.com`。
- **原因**：
  - ⚠️ **先澄清一个容易误判的点**：本项目前端 `.env.production` 用的是 `VITE_API_BASE=/api`（相对路径），
    生产走**同域反向代理**，此时浏览器**根本不会发起跨域请求**，CORS 配置不生效也不报错。
  - 但正因为"不生效也不报错"，**将来一旦改成前后端不同域（如前端放 CDN、后端放 API 域名），
    当前的 localhost 白名单会让所有请求 403，而排查方向会误以为是 Nginx 或 token 问题**。
    所以现在就把环境变量留好，是给未来省一次事故。
  - 另注：`WebMvcConfig` 里 `allowCredentials(false)` 是**正确的**（鉴权走 Authorization 头，不走 Cookie），
    保持不动。切勿为了"支持跨域"改成 `true` —— 通配来源 + 允许凭据是危险组合。

## 2. 依赖与构建

### P0-5　★★ 时区必须三处统一，否则「在线」功能整体静默失效

- **现状**（这是本次审查发现的**最隐蔽的一处**）：
  - **写入**：`UserService.java:214` → `.set(User::getLastActiveAt, LocalDateTime.now())`（**JVM 时区**）
  - **读取**：`UserService.java:256` → `.apply("last_active_at > DATE_SUB(NOW(), INTERVAL 300 SECOND)")`（**MySQL 服务器时区**）
  - `application.yml:46` 里的 `serverTimezone=Asia/Shanghai` 是 **Connector/J 5.x 时代的参数名**，
    在 8.x 下**不改变会话时区**，所以它**不能**解决这个问题。
- **后果**：服务器 MySQL 若是 UTC（**Docker 官方 `mysql` 镜像默认就是 UTC**）而 JVM 是 `Asia/Shanghai`，
  两者相差 8 小时 → `last_active_at` 永远小于 `NOW() - 300s` →
  **全站所有人永久显示离线**（反向则永久在线）。而**不会产生任何错误日志**，
  只会表现为"在线小绿点怎么都不亮"。
- **改法**（三处一起做，任一处漏掉都可能复现）：
  1. JVM 启动参数：`-Duser.timezone=Asia/Shanghai`
  2. JDBC URL 追加：`&connectionTimeZone=Asia/Shanghai&forceConnectionTimeZoneToSession=true`
     （`forceConnectionTimeZoneToSession=true` 会**强制设置 MySQL 会话时区**，这是让 `NOW()` 与 JVM 对齐的关键）
  3. 容器/主机侧统一：`TZ=Asia/Shanghai`（Docker）或 MySQL `default-time-zone='+08:00'`
- **顺带影响**：`UploadController.java:103` 用 `LocalDate.now()` 决定上传目录的 `yyyy/MM` 分片，
  同样依赖 JVM 时区；时区不统一时会出现"同一个月的图分散在两个目录"。
- **验证方式**：部署后执行
  ```sql
  SELECT NOW() AS mysql_now, @@global.time_zone, @@session.time_zone;
  ```
  再与 `curl` 接口返回的 `createTime`（Jackson 已固定 `Asia/Shanghai`）比对，两者应一致。

### P0-6　补 Maven Wrapper，构建不再依赖"服务器上恰好装了对的 Maven"

> ✅ **已落地（2026-09-22）**。生成物：`mvnw`、`mvnw.cmd`、`.mvn/wrapper/maven-wrapper.properties`。
> 两点与清单原方案不同的取舍：
>
> 1. **用 `only-script` 模式，不落 `maven-wrapper.jar`** —— wrapper 3.2+ 支持脚本自行下载发行版，
>    省掉一个二进制文件（仓库里少一个"看不懂的东西"，也不用为它配 `.gitignore` 例外）；
> 2. **`distributionUrl` 指向阿里云**（`https://maven.aliyun.com/repository/public/...`）
>    而不是默认的 `repo.maven.apache.org` —— 目标机器在国内时这是"能不能下下来"的区别。
>
> 真机验证：`.\mvnw.cmd -v` 输出 `Apache Maven 3.9.4` / `Java version: 17`，
> 首次运行自动把发行版解到 `~/.m2/wrapper/dists/apache-maven-3.9.4/<hash>/`。
> ⇒ **服务器上只需要 JDK 17，不需要预装 Maven。**

- **现状**：无 `mvnw` / `mvnw.cmd`；本机用的是 `D:\apache-maven-3.9.4`。
- **改法**：在后端目录执行一次 `mvn -N wrapper:wrapper -Dmaven=3.9.4`，
  之后部署脚本统一用 `./mvnw -DskipTests package`。
- **原因**：`pom.xml` 没钉 Maven 版本，服务器上装的是 3.6/3.8 也可能打出不一样的包；
  更常见的是服务器**压根没装 Maven**。Wrapper 把构建工具变成仓库里的一份文件，
  这是"我这儿能打包、服务器上不行"最便宜的解法。

### P0-7　Spring AI 依赖指向 milestone 仓库 —— 服务器可能构建失败

> ✅ **已关闭（2026-09-22），采用的是上面推荐的方案 1（服务器不构建，只收 jar）。**
>
> **为什么没有选方案 2（升 GA）**：官方升级说明写明 **Spring AI 1.0.0 GA 及之后只支持
> Spring Boot 3.4.x / 3.5.x**，而本项目父工程是 3.2.5。也就是说"把 spring-ai 升上去"
> 实际会拖出一次 **Spring Boot 大版本迁移**（MyBatis-Plus、springdoc 都要跟着升，
> 371 个单测与全部真机探针要重新回归）。那属于**独立的一批依赖升级**，
> 不该借"部署适配"之手顺手做掉 —— 混在一起出问题时，无法判断是迁移引入的还是部署引入的。
>
> **方案 1 落地成了什么（不只是文档里一句话）**：`deploy/build-release.mjs`，在**开发机/CI** 运行：
> 1. 用 `mvnw -Pprod` 打包；
> 2. 产物重命名为 `campus-market-<版本>-<commit|源码指纹>-<时间>.jar`；
> 3. 产出 `.sha256` 与 `.info.txt`（记录版本、源码指纹、构建环境）；
> 4. ★ **自检产物**：解 jar 检查 demo 资源必须为 0、`logback-spring.xml` 与
>    `application-prod.yml` 必须存在，否则**退出码 2 拒绝产出发布件**。
>
> 这条自检做过红绿（`.workbuddy/probe-build-selfcheck.mjs`）：
> 摘掉 `-Pprod` 后它以退出码 2 拦下，并逐条点名 6 个 demo 文件；还原后字节一致、复绿。
>
> ⚠️ **顺带发现**：本仓库**不是 git 仓库**（有 `.github/` 但没有 `.git`）。
> 因此产物名里的标识来自**源码指纹**（`src/` + `pom.xml` 的内容摘要），
> 它仍能回答"两个包是不是同一份代码"，但**无法反查历史**。
> 正式发版前建议先 `git init`，否则"线上跑的是哪次提交"这个问题永远没有答案。
>
> ★★ **追加关闭：构建可复现（2026-09-22）** ★★
>
> 动手做 P1-3 时实测到一件比清单预想更严重的事：
> `dist/` 里出现**两个不同大小**的产物（53764139B vs 53764901B）。
> 逐条比对 → **73 个条目内容不同**（含 72 个我方 `.class`），依赖 jar 完全没变。
> `javap` 反汇编定位根因：字符串拼接的降级策略不同，
> `invokedynamic makeConcatWithConstants` vs `String.valueOf` + indy，常量池 122 条 vs 128 条。
> **真正的原因**：本机 `JAVA_HOME` 指向 `D:\Android\Android Studio\jbr`，
> 那是 Android Studio 自带的 JetBrains Runtime，**是 Java 21**；
> 而手工构建用的是 `jdk-17`（实测 `mvnw.cmd -v`：JBR → `Java 21.0.10`，jdk-17 → `Java 17`）。
>
> 后果不是"小差异"：**产物取决于开发机当时开着什么 IDE**。
> 那么"我测过的包"和"我发出去的包"就无法用任何哈希对上 ——
> 而哈希恰好是"服务器上跑的是不是我验过的那份"唯一能靠的东西。
> 换句话说，**没有可复现构建，P1-3 的版本化与 sha256 只是好看的装饰**。
>
> 修法两条，缺一不可：
> 1. `pom.xml` 加 `<project.build.outputTimestamp>2026-01-01T00:00:00Z`，
>    钉死 jar 条目时间戳（用常量而非构建时间，否则等于没钉）；
> 2. `deploy/build-release.mjs` **不信任环境变量**：自己解析出真正的 JDK 17
>    （顺序：`--java-home=` > `JDK17_HOME` > 已是 17 的 `JAVA_HOME` > 常见安装路径），
>    覆盖 `JAVA_HOME` 后再调 `mvnw`，并把解析过程打印出来（可复核）；
>    一个都找不到就**退出码 2 直接失败**，绝不"凑合用 21 也能编"。
>
> 判据是**同一份源码连跑两次、产物 sha256 逐字节相同**，由 `.workbuddy/probe-reproducible.mjs` 证明。
> 这个探针刻意做成**三轮**：
> `run1` / `run2` 走发版脚本 ⇒ 必须**相同**（可复现）；
> `run3` 绕过发版脚本、故意用那个 JBR(21) 编 ⇒ 必须**不同**。
> 第三轮不是多余的 —— 「连跑两次得到同一个 sha」只证明了两件事相同，
> **没证明这两件事是什么**；一个坏掉的探针（比对了同一个文件、读到空值）同样会输出"相同"。
> 没有对照组，这个"绿"就是没有判别力的绿。

- **现状**：`pom.xml:27` `${spring-ai.version}=1.0.0-M6`（里程碑版），
  `pom.xml:121-129` 额外声明了 `https://repo.spring.io/milestone`。
- **问题**：里程碑版本**不在 Maven Central**。服务器若在无外网/只放行国内镜像的环境里构建，
  **`repo.spring.io` 拿不到 → 构建直接失败**。本机是靠 `aliyun-settings.xml` + 能访问 spring 仓库才通的。
- **改法**（三选一，按推荐排序）：
  1. **推荐**：构建在 CI / 本机完成，服务器**只接收 jar 产物**，不构建（最省事、最可控）；
  2. 把 Spring AI 升到 GA 版本（`1.0.0` 正式版已发布）→ 可从 Central 拉，去掉 milestone 仓库；
  3. 内网私服（Nexus）预热依赖，服务器从私服拉。
- **原因**：把"能不能连上境外 Maven 仓库"变成上线的前置条件，是最不必要的一类故障源。

### P1-3　产物版本化 + 校验和

> ✅ **已落地（2026-09-22）**，与 P0-7 同一批（两者本就互为前提：**不可复现的产物，版本化与 sha256 只是装饰**）。
>
> - 产物重命名：`campus-market-<版本>-<commit|源码指纹>-<yyyyMMddHHmm>.jar`；
> - 同目录产出 `.sha256`（`sha256sum -c` 可直接校验）与 `.info.txt`
>   （记录版本、revision、源码指纹、构建时间、**实际使用的 JDK**、profile、sha256）；
> - `deploy/build-release.mjs` 收尾直接把服务器侧三条命令打印出来（上传 → 校验 → 装/重启），
>   交接时不用去翻聊天记录找命令；
> - `dist/` 已加入 `.gitignore`。
>
> 三点与原方案的差异（都是踩出来的）：
> 1. 原方案用 `-DbuildNumber=$(git rev-parse --short HEAD)`。本仓库**无 git**，
>    故优先用 commit，**退化为源码指纹**（`src/` + `pom.xml` 共 170 个文件的排序内容摘要）。
>    它仍能回答"两个包是不是同一份代码"，但**无法反查历史**。
> 2. 原方案用 `spring-boot-maven-plugin` 的 `<buildInfo />`。**没有采用** ——
>    它会把构建时间写进 `BOOT-INF/classes/META-INF/build-info.properties`，
>    **正好破坏刚刚建立的可复现性**（时间每次不同 ⇒ 哈希每次都不同）。
>    改用外部的 `.info.txt` 记录同样的信息，不污染产物字节。
> 3. `.info.txt` 里的 `java` 一行记的是**脚本实际使用的 JDK**，
>    并单列 `javaHomeEnv` 记录被忽略掉的环境变量。若这里错记成 `JAVA_HOME`，
>    日后的"复现不出来"会被误导到错误方向。

- **现状**：产物固定为 `target/campus-secondhand-backend-1.0.0.jar`，无版本标识。
- **改法**：构建时用 `-DbuildNumber=$(git rev-parse --short HEAD)-$(date +%Y%m%d%H%M)`
  配合 `spring-boot-maven-plugin` 的 `<buildInfo />`，产物重命名带版本；发布时记录 `sha256sum`。
- **原因**：线上出问题时第一个要回答的是"现在跑的是哪个 commit"。
  固定文件名的 jar 在多次发布后就无法回溯，只能靠时间猜。

### P1-4　提供一份可复现的部署载体（Dockerfile / compose / systemd，任选其一）

- **现状**：无 `Dockerfile`、无 `docker-compose.yml`、无 systemd unit、无部署脚本。
- **改法**：给出其中一套并纳入仓库。以 systemd 为例（最简单，适合课程交付）：
  ```ini
  # /etc/systemd/system/campus-market.service
  [Service]
  User=campus
  WorkingDirectory=/opt/campus-market
  EnvironmentFile=/etc/campus-market/env            # 凭据只在这里
  ExecStart=/usr/bin/java -Duser.timezone=Asia/Shanghai \
            -Xms512m -Xmx1g -XX:+UseG1GC \
            -jar /opt/campus-market/app.jar --spring.profiles.active=prod
  SuccessExitStatus=143                              # 优雅停机被 SIGTERM 终止时退出码是 143
  Restart=on-failure
  RestartSec=5
  [Service]
  ```
  **注意**：`SuccessExitStatus=143` 必须加，否则每次正常停服都会被 systemd 判为失败并触发重启。
- **原因**：手工 `java -jar` + 手配 Nginx 的过程不可复现、无法 code review，
  而且**凭据会散落在 shell 历史里**（`export DB_PASSWORD=...` 会被记进 `.bash_history`）。

### P2-2　前端构建：用 `npm ci`，并钉住 Node 版本

- **现状**：`package-lock.json` **已存在** ✅（这点很好）；但无 `.nvmrc`，无 `packageManager` 字段。
- **改法**：构建命令用 `npm ci`（**不是 `npm install`**）；加 `.nvmrc`（内容 `18.19.0`）或

### ✅ P2-3　前端 `base` 未配置 —— 部署在子路径会全站 404（已修 · 2026-09-23）

> **已落地**：`base` 与路由 history 的 base **成对**取自 Vite 注入的 `BASE_URL`：
> - `vite.config.ts`：`base: env.VITE_BASE || '/'`（默认 `/`，对根域名部署**零影响**）；
> - `src/router/index.ts`：`createWebHistory(import.meta.env.BASE_URL)`；
> - `.env.production`：新增 `VITE_BASE=/`，子路径部署**只改这一处**。
>
> ★ **为什么必须成对** ★ 只改打包 `base` ⇒ 资源在 `/market/assets/`、路由仍按根解析
> ⇒「首页打得开、点任何导航就 404」；只改路由 ⇒ 反过来资源全裂。
> 这两个残缺状态**各自都像"能跑"**，所以审计判据要求两者同时成立（`audit-deploy-gap.mjs` P2-3）。
>
> ⚠️ 仍然要记住：`/api/**`（接口）与 `/uploads/**`（图片）是**绝对路径**
> （库里存的就是 `/uploads/2026/09/xxx.jpg`），Nginx 那两条反代规则**不随 base 变化**。
>
> 证据：前端 `vitest` **727/727**、`vue-tsc` 0 错；两份前端副本 `sync-check` 一致；
> 审计脚本回代码实测 `base=env.VITE_BASE || '/' · router=createWebHistory(BASE_URL)`。

- **原问题**：`vite.config.ts` 未设 `base`（默认 `/`）。
- **改法**：若部署在根域名（`https://host/`）→ 不用改；
  若部署在子路径（`https://host/campus/`）→ 必须设 `base: '/campus/'`，并同步调整 Nginx 前缀。
- **原因**：产物里的资源引用是绝对路径（`/assets/xxx.js`），子路径下会去根目录找 → 全白屏。
  另外注意 `vite.config.ts:61-65` 对 `/uploads` 的代理说明里已经写明：
  **生产要由 Nginx 把 `/uploads` 转发到后端的 `/api/uploads`**（因为后端 `context-path=/api`），
  这条漏了就是**商品图整片裂开**。这是最容易漏的一条 Nginx 规则。

### P0-8　加日志落盘（当前只有 console）

> ✅ **已落地（2026-09-22）**：`src/main/resources/logback-spring.xml`（3231 字节，已打进 jar）。
>
> 落地方案：按天 **+** 按大小 `SizeAndTimeBasedRollingPolicy`（100MB 切分）、
> 保留 30 天、总量上限 2GB、`cleanHistoryOnStart`、**ERROR 单独一份**（`campus-market-error.log`）。
> 目录由 `app.log-dir` 决定（本地 `logs`、prod `/data/campus/logs`），可用 `LOG_DIR` 覆盖。
>
> 四个刻意的决定：
> 1. **控制台不显式设 charset** —— Windows 控制台是 GBK，写死 UTF-8 会让本机启动日志中文全乱码，
>    而项目的真机探针本来就是按 GBK 解码控制台输出的。不写 ⇒ 跟随 JVM 默认编码，
>    **落盘文件**则固定 UTF-8（便于 grep 与交接）；
> 2. **不在本文件里写 `<logger>` 级别** —— 级别统一由 `application*.yml` 的 `logging.level` 决定。
>    两处都能配级别 = 两个开关（本项目反复强调要避免的形态）；
> 3. **不配 `logging.file.path`** —— 它会与 `<file>` 打架，谁生效取决于加载顺序；
> 4. **默认往 `logs/` 写**（而不是"只在 prod 才写文件"）—— 否则这个能力在开发机上永远得不到验证，
>    而"配了但没生效"正是本项目踩过最多的坑。`logs/` 已在 `.gitignore` 里。
>
> 真机验证：`.workbuddy/e2e-logging.mjs` **11 PASS / 0 FAIL**，两组场景：
> ① 默认启动 → `logs/` 下两个文件出现且有内容、错误文件里**没有非 ERROR 行**；
> ② ★ 显式 `--app.log-dir=<自定义>` → 文件落到自定义目录，且**默认目录没有被再创建**。
> 第 ② 组才是关键：只测 ① 的话，`<springProperty>` 的 `source` 写错名也会照样落到默认目录，
> ① 仍旧全绿 —— 那就是"配置项是死的"而没人发现。

- **现状**：**没有 `logback-spring.xml`**，Spring Boot 默认只输出到标准输出，无文件、无滚动、无保留策略。
- **改法**：加 `logback-spring.xml`：按天滚动 + 保留 30 天 + 总大小上限 + 单独 `error` 文件。
  或明确选择"日志交给 systemd/journald"，**但必须在部署文档里写清 `journalctl -u campus-market` 的用法与保留策略**
  （journald 默认可能被 `Storage=auto` + 系统配额静默截断，出故障时发现日志没了）。
- **原因**：只输出 console 时，进程重启日志即丢。生产排障的第一现场是日志，
  **"日志在哪、留多久"必须在部署前有答案**，不能等出事再找。

### ✅ P1-5　健康检查端点（已修 · 2026-09-22 · B6 批）

- **当时的现状**：`pom.xml` **无 `spring-boot-starter-actuator`**，全仓无 `/health`、`/ping` 端点；
  而 `GlobalExceptionHandler` 与 `AuthInterceptor.reject()` **统一返回 HTTP 200**，业务码放在 body。
- **当时的后果**：Nginx upstream 健康检查、云监控、负载均衡探针**全部失效** ——
  数据库连不上、接口全线 500，探针看到的仍是 `200 OK`。**服务已经挂了，监控显示健康。**
- **实际做法（与原文建议有四处刻意不同）**：
  1. **不引 actuator，自建 `GET /health`**（`HealthController` + `HealthService`）。理由：
     actuator 会一并带来 `/env`、`/beans` 等端点（多一片泄露面），且它的健康口径与本项目
     「错误一律 HTTP 200」的契约不一致，运维得记两套规则。自建只有十几行，口径完全统一。
  2. **三态而不是两态**：`UP` / `DEGRADED`（库好、日志目录不可写）/ `DOWN`（库不可用）。
     把 DEGRADED 报成 DOWN 会让告警失真（狼来了），把它报成 UP 又等于没检查 —— 两者处置动作不同。
  3. **探测自带超时**（`app.health.db-timeout-ms`，默认 2000ms；下限夹紧到 200ms）：
     库挂住时 Hikari 的 `getConnection()` 会等 30 秒 ⇒ 探针自己先挂住 ⇒ 监控判探针超时 ⇒
     「探针看不出故障」退化成「探针自己不可用」。配置配 `0`/负数**收敛到 200ms**
     （本仓「0=不限」的口径**不适用于时限**：没有"无限等"这种选项）。
  4. **不回传内部细节**：`data.log` 只报 `writable`，不带绝对路径（该端点匿名可读）。
- **监控口径（★ 关键）**：端点**恒返回 HTTP 200**（沿用前端契约，不要改），
  **必须判 `data.status`，不要看状态码**；只有真正未捕获的异常才由 `code=500` 表示。
- **白名单**：`AuthInterceptor.PUBLIC_GET` 加 `/health` —— **只放行 GET**，POST 仍未登录即 401。
- **证据**：单测 `HealthServiceTest`(9) + `HealthControllerTest`(3)；红绿 5 轮；判据红绿 4 轮；
  真机 `e2e-p15p16`（含「库不可用报 DOWN」「卡住的依赖必须算不健康」）。详见 §7.7。

### ✅ P1-6　异常日志带请求上下文（已修 · 2026-09-22 · B6 批）

- **当时的现状**：兜底分支只记 `log.error("未捕获异常", e)`，没有请求信息。
  生产上"有一个 500"最需要知道的是**哪个接口、哪个用户**，只有堆栈和时间戳就只能靠时间窗猜。
- **实际做法**：
  1. `RequestTraceFilter`（`OncePerRequestFilter` + `HIGHEST_PRECEDENCE`）在**请求入口**设置
     `traceId / method / uri`；`uid` 由 `AuthInterceptor` 在解析出身份后补入
     （过滤器不参与鉴权，也就不该知道"谁"）。
     **为什么不用清单建议的"在拦截器里 `MDC.put`"**：`preHandle` **晚于**
     `NoResourceFoundException`（路由不存在，本项目也兜成 200）与 Servlet 容器层的拒绝 ——
     那些请求**根本进不到拦截器**，日志仍是没有上下文的孤行。
  2. **traceId 优先沿用调用方的 `X-Request-Id`**（Nginx 用 `$request_id` 生成并透传，
     两侧同一个 id 才能跨层串起来），并**回写响应头**（连带 `Access-Control-Expose-Headers`，
     否则浏览器读不到）—— 用户报障时能直接把 id 给运维，否则"我们有了 traceId 也没人告诉我们是哪次"。
  3. ★ **白名单校验，防日志注入**：头是**攻击者可控**输入，原样进 MDC 再进日志，
     塞 `\r\n` 就能**凭空伪造一整行日志**（例如伪造一条 `ERROR 支付失败` 让值班的人去查不存在的事故）。
     只接受 `[A-Za-z0-9_-]{8,64}`，不合法就**丢弃并重新生成** ——
     即「不合法的输入不进日志」，而不是「进日志但转义」（转义漏一个字符就前功尽弃）。
     URI 字段风险面不同：不能白名单（本来就可能有中文/百分号），只**去控制字符 + 截断 200**。
  4. **清理写在 `finally`**（`MDC.clear()`）：线程是复用的，不清就是
     **下一个请求顶着上一个请求的身份**，而这种错乱只在并发下出现、本地几乎复现不出来。
  5. `logback-spring.xml` 的 `FILE_PATTERN` 带上
     `[%X{traceId:-}] [uid=%X{uid:-anon}] [%X{method:-?} %X{uri:-?}]`
     （**漏了 `:-` 默认值会打空串，肉眼几乎看不出**）；
     定时任务不在请求线程上，`GoodsOfflineJob` 自设 `traceId=job-goods-offline-<毫秒>`
     并在 `finally` 清掉（时间戳不是装饰：同一任务的两次执行必须能分开，
     否则"昨天失败了没有"查不出来）。
- **已知边界（如实交代）**：**成功的请求一行日志都不打**（本项目没有 access log），
  所以「每行日志都带上下文」的价值只在**真打了日志的那些行**（异常/告警）上兑现 ——
  而那正是排障要的那一行。异步任务与子线程不在覆盖范围内。
- **证据**：单测 `RequestTraceFilterTest`(7)；红绿 5 轮；真机 `e2e-p15p16`
  （含「非法 id 既不回写、也不进日志」）。详见 §7.7。

### ✅ P1-10　上传接口没有次数上限、也不看文件内容（已修 · 2026-09-23 · B7 批）

- **当时的现状**：`POST /upload/image` 已有三条校验 —— 非空、`app.upload.max-image-bytes` 字节上限、
  扩展名白名单 —— **但三条都与「传了多少次」「传的到底是什么」无关**：
  1. **次数上没有任何约束**。任何一个登录账号写个 `for` 循环，几分钟就能往服务器磁盘写进几万个文件。
     上传目录里装的是**业务数据，不可回收、不能随部署覆盖**，写满会连带数据库与日志写不进去。
  2. **内容判定靠 `Content-Type` 前缀与客户端给的文件名后缀**。前者的值由客户端自己声明
     （改一个字就过），后者与「这段字节真的是图片吗」没有任何强制关系 ⇒
     `evil.png` 里装一段 HTML / 一段脚本 / 一个压缩炸弹，都能拿到一个**可公开访问**的 URL。
- **实际做法**：
  1. **魔数嗅探取代声明与后缀**（`common/ImageType`）：只读文件头 `HEAD_LENGTH = 12` 字节，
     按字节判定 JPEG / PNG / GIF / WEBP / BMP，识别不出即**拒收**。
     落盘扩展名**取自嗅探结果**（一个封闭的 5 元素集合），比白名单更强；客户端提供的名字
     **一个字符都不进入落盘路径**（UUID 重命名 + 字节扩展名）。
     WEBP 是 RIFF 容器、签名分两段（偏移 0 的 `RIFF` + 偏移 8 的 `WEBP`），所以统一读 12 字节。
     只读文件头而**刻意不用 `file.getBytes()`**：后者把 2MB 整份读进堆，几十个并发就能顶出 OOM。
  2. **次数闸门双维度**（`security/UploadQuotaGuard`）：用户维度 `user-max-uploads`（默认 10）管**公平**，
     全站维度 `global-max-uploads`（默认 60）管**容量**，任一命中即拒。
     用户维度拦不住「注册 100 个账号各传 9 张」，全站维度才是真正兜住磁盘的那张网。
  3. ★ **校验顺序本身是设计**：闸门 → 非空 → 字节上限 → 魔数。闸门是唯一**不读文件内容**的检查，
     必须最先；排在魔数之后会出现反直觉后果 —— 攻击者用**永远不合法**的文件猛发，
     每次都在更贵的分支上被拒，**闸门却一次都没计数**。
  4. 「判定两个维度」与「两个维度各自 +1」在**同一临界区、共用一把锁**内完成：
     分开会出现「用户维度判过、全站同时被别人顶满」，这次既不该放行、用户计数却已被吃掉。
     判定时**先判全站、再建用户条目**（判得越早代价越小，也不留内存痕迹）。
  5. **配置口径**沿用本仓既有约定：`0` / 负数 = 该维度不限；**唯独 `window-seconds` 配 0 收敛到 1 秒**
     —— 窗口恒为零会让计数永远从 0 开始，闸门静默失效而配置看起来"只是设小了一点"。
     三个键**只在 `application.yml` 一处定义**，prod 不重复声明（同一概念两个开关，日后必错一个）。
  6. 拒绝提示里带上**生效的窗口与额度数字**，让「配置有没有到达变量」有一个**响应体上的可观测出口**：
     真机探针据此断言提示里必须出现命令行注入的 `3` 与 `60`。
- **已知边界（如实交代）**：闸门是**纯内存、单实例有效**，多实例各算各的（总容忍度放大 N 倍），
  重启即清零 —— 它挡的是「持续滥用」，不是「重启即绕过」；后者要靠部署侧的磁盘配额与监控兜。
  魔数只保证「是不是这几种图片容器」，**不校验解码后的内容**（畸形结构、压缩炸弹仍需后续环节防护）。
- **证据**：单测 `ImageTypeTest`(9) + `UploadQuotaGuardTest`(13) + `UploadControllerTest`(11)；
  红绿 11 轮；判据红绿 7 轮；真机 `e2e-p110` 跑**两个产物**（两侧各 10 PASS / 0 FAIL）。详见 §7.8。

## 4. 安全与权限

### P0-10　必须上 HTTPS（当前全链路明文）

- **现状**：无任何 TLS 配置；JDBC 也是 `useSSL=false`。
- **改法**：Nginx 终止 TLS（Let's Encrypt 或自有证书），HTTP 301 跳 HTTPS，
  并加 HSTS；后端只监听 `127.0.0.1:8080`（**不要 `0.0.0.0`**，不经过 Nginx 的请求一律不可达）。
- **原因**：本项目鉴权是 `Authorization: Bearer <JWT>`。明文 HTTP 下，
  同一网络内的任何人都能**直接抓到 token 并冒充该用户 24 小时**（`jwt.expiration=86400000`）。
  另外把 Tomcat 绑到 `127.0.0.1` 是关键的一点：否则可以绕过 Nginx 直连 8080，
  **所有在 Nginx 层做的限流、TLS、访问控制全部失效**。

### P1-7　登录接口无任何限流 —— 在线必被爆破

- **现状**：全仓检索 `RateLimiter` / `bucket4j` / `sentinel` / 失败计数 **0 命中**。
  `POST /user/login` 可无限次尝试。
- **改法**（按投入排序）：
  1. 最省事：Nginx `limit_req_zone` 对 `/api/user/login` 限速（如 5r/m），`limit_req_status 429`；
  2. 应用层：按 `username` + IP 记录失败次数，5 次后阶梯延迟/锁定 15 分钟
     （表或 Caffeine 本地缓存，单实例用本地缓存即可）。
- **原因**：种子密码是 `admin123` 这类弱口令（见 P1-8），且用户名可从商品列表直接看到，
  等于**公开的用户名 + 可无限试的弱口令**。这是公网部署后最先被扫的两个点之一（另一个是上传接口）。

### P1-8　种子里的弱口令账号在生产必须处理

- **现状**：`db/seed-base.sql` 里是固定口令（`admin/admin123` 等），且口令是 BCrypt 哈希**明文写在仓库里**。
- **改法**：
  - 生产**不执行 `seed-base.sql`**（配合 P1-9 的 `mode: never`），管理员账号单独手工创建；
  - 或部署后**立即**通过后台改密，并把该步骤写进上线检查表（不可省略）。
- **原因**：仓库公开 = 口令公开。生产上线后如果没人记得改，这个后台就是敞开的。
  注意这条与"本地演示零配置可登录"是冲突的，**冲突的解法是 profile 区分，而不是删掉种子**。

### P1-9　`spring.sql.init.mode` 生产要关掉

- **现状**：`application.yml:77` `mode: always` → **每次启动都执行 DDL**。
- **改法**：`application-prod.yml` 设 `mode: never`；建表/升级改为**显式执行一次**（或用 Flyway/Liquibase）。
- **原因**：
  - `schema-auto.sql` 是 `CREATE TABLE IF NOT EXISTS`，本身幂等安全 —— 所以**不是紧急缺陷**；
  - 但两点隐患：① 每次启动都跑一遍 DDL 需要 DDL 权限，与 P1-2 的"只给 CRUD"矛盾；
    ② 它**只建表、不补列**，老库加列必须靠手工增量脚本，容易在部署时被遗忘（`application.yml:73` 已写明这个限制）。
  - 生产把"结构变更"从"启动副作用"里拿出来，变成一次受控操作，是更稳的做法。

### P1-10　上传接口：无限流、无内容嗅探

- **现状**：`UploadController` 已做对的部分很多 ——
  大小限制（2MB）、`Content-Type` 前缀校验、**扩展名白名单**、
  **文件名一律重新生成**（`UUID`，只取扩展名 → 天然免疫 `../` 路径穿越）、
  落盘用绝对路径、按 `yyyy/MM` 分片，且上传接口**需要登录**（不在白名单里）。
- **仍缺**：
  1. **无频率限制** → 单个已登录账号可反复上传把磁盘刷满；
  2. **无内容嗅探** → `Content-Type` 与扩展名都是客户端声明的，
     传一个 HTML/脚本内容的文件并命名为 `.jpg` 可以落盘。
     （**风险有限**：静态资源由 Spring 按扩展名返回 `image/jpeg`，浏览器不会当 HTML 执行，
     所以不是 XSS 级问题；但**会白占磁盘**，且属于"上传了不该上传的东西"。）
- **改法**：① 上传接口限流（如 10 次/分钟/用户）；② 读前 8 字节校验文件魔数
  （JPEG `FF D8 FF`、PNG `89 50 4E 47`、GIF `47 49 46`、WEBP `RIFF....WEBP`）；
  ③ 加磁盘水位告警。
- **原因**：公网环境下，**允许写文件的接口是磁盘耗尽的主要入口**。

### P2-4　上传大小三层口径要一致

- **现状**：三处限制不同 —— Spring `multipart.max-file-size: 5MB`（`application.yml:31`）、
  应用层 `app.upload.max-image-bytes: 2097152`（2MB）、前端压缩后约 100~400KB。
  `application.yml:28` 的注释已经提示"三者口径别打架"。
- **改法**：公网部署建议把 multipart 收到 `2MB`（与应用层一致），或至少明确"谁先拦"。
- **原因**：不一致时用户会看到"传了 3MB 的图，报的是后端的错而不是大小超限"，提示与真实原因不符。

## 5. 性能与资源占用

### ✅ P1-11　每个已登录请求都多一次 `selectById` —— 缺少缓存层（已修 · 2026-09-23）

> **已落地**：`AuthSnapshotCache`（Caffeine，**只引 `caffeine`，不引 `spring-boot-starter-cache`**）
> 接管了那次回查 —— 语义没变（仍然"以库为准、不信 token"），变的是代价：
> 从「每请求一次主键查询」降到「**每用户每 10 秒一次**」。
>
> **为什么不引 `spring-boot-starter-cache`**：那会带来注解式缓存（`@Cacheable`）
> 与 AOP 代理。而本项目这一层要的是"**显式失效**"—— 封禁/改密必须**当场**生效，
> 交给注解与代理只会多出"自调用不生效 / 代理没配上"的静默失效角落（本仓栽过）。
> 显式调用只多一行，却能一眼看出谁在什么时候失效。
>
> **两道保障（缺一不可）**：
> 1. **6 个鉴权列写入点全部显式失效**（`approveUser` / `toggleUserStatus` /
>    `batchToggleUserStatus` / `resetUserPassword` / `changePassword` / 举报处置的 ban）
>    ⇒ 撤销**立即**生效，不是"最多慢 10 秒"；
> 2. **TTL 兜底**（`expireAfterWrite(10s)`）⇒ 万一将来新增了写点忘了接线，最坏也只是慢 10 秒，
>    不会永久泄漏。`AuthCacheInvalidationTest#everyAuthColumnWriteInvalidates` 是一条
>    **源码看守**，新增写点没接失效就会报红。
>
> ★ **心跳是这一层最容易踩的坑** ★ `UserService#heartbeat` 每 60 秒写一次 `last_active_at`。
> 失效若锚在「任何 `t_user` 写入」上，缓存会被心跳持续冲掉 —— 等于白做。
> 所以判据锚的是**那三列**（status / role / token_version），并且有一条**反向对照**用例
> （`heartbeatDoesNotFlushTheAuthCache`）专门守着这件事。
>
> 证据（四层）：
> - 单测 **18 条**（`AuthSnapshotCacheTest` 10 + `AuthCacheInvalidationTest` 8）
>   + 拦截器快照 **5 条**；后端全量 **470/470**；
> - 红绿探针 `.workbuddy/probe-p111-redgreen.mjs` **9 轮 0 异常**
>   （含 R0/RC 对照组、R6 反向对照、R5 看守自证）；每轮同时点名「必须红」与「必须仍绿」；
> - 判据红绿：审计里这一项从「只看 pom 有没有 caffeine」改成锚能力（依赖 + 拦截器经缓存
>   + 不再直查 + TTL 兜底 + 失效点 ≥6）；
> - 真机 `.workbuddy/e2e-p111.mjs` 跑**两个产物**（两侧各 **16 PASS / 0 FAIL**）：
>   修复后 `a9b773315108` 下「直改库封禁后 28ms 仍放行、8.3 秒后才转 401」；
>   修复前 `cbdf3841d484` 下**同一判据 12ms 就直接 401** ⇒ 「缓存存在」这项能力确实随版本出现。
>   详见 §7.10。

- **原问题**：`AuthInterceptor.java:174` 每个已登录请求都
  `userMapper.selectById(...)` 回查 `t_user`（用于封禁/降权/`token_version` 即时生效）。
  代码注释已说明这是**有意为之的正确权衡**（"撤销权限要撤得干净"）。
- **改法（原建议）**：加 `spring-boot-starter-cache` + Caffeine，给这次回查加 **5~30 秒 TTL 的本地缓存**，
  并在封禁/改密/改角色时**主动失效**该 key。
  ▲ **落地时的两处订正**（理由见本节开头的 ✅ 块与 §7.10）：
  ① **不引** `spring-boot-starter-cache`，只引 `caffeine` —— 要的是显式失效，不是注解式切面；
  ② TTL 取 **10 秒的常量**（不是可配的 5~30 秒）—— 这个数字是**安全边界**而非性能旋钮，
     做成配置项等于给运维留一个「调大一点更快」而**不报任何错**的坑。
- **原因**：
  - 代价是**所有业务接口都多一次数据库往返**（1 次主键查询 + 1 次网络往返）；
  - 更关键的是它**先于业务逻辑占用连接**：并发一上来，15 个 Hikari 连接会被这一层先吃掉，
    表现为"业务查询还没开始就在等连接"；
  - 短 TTL 缓存把"撤销延迟"从 0 秒放宽到最大 30 秒 —— 对封禁场景完全可接受
    （前端 `recheckSession` 那条链路的实时性本来也不是硬需求）。
  - ⚠️ **注意**：`pom.xml` 目前**没有** `spring-boot-starter-cache`，
    也没有 Redis/Caffeine，所以这是"要新增依赖"的改动，不是配置调整。

### P1-12　连接池、线程数、JVM 堆要一起算，别各调各的

- **现状**：Hikari `maximum-pool-size: 15`、`minimum-idle: 5`（`application.yml:50-54`）；
  Tomcat `max-threads: 200`、`accept-count: 50`（`:15-16`）；JVM 未给堆参数。
- **问题**：
  - **200 个 Tomcat 线程去抢 15 个数据库连接** —— 连接池会先成为瓶颈，
    而 200 个线程同时排队等待会让 `connection-timeout: 30000` 大量触发（表现为 500 + 连接超时日志）；
  - 多实例部署时 `15 × N` 可能超过 MySQL `max_connections`（默认 151）；
  - JVM 未设堆 → 默认取物理内存 1/4，小内存服务器上容易 OOM 或被 OOM Killer 杀掉。
- **改法**（以 2 核 4G 单实例为例）：
  ```
  max-pool-size ≈ min(2 × CPU核数, MySQL.max_connections / 实例数)   → 2核取 8~10
  max-threads   ≈ max-pool-size × (2~4)                              → 取 50，不要 200
  JVM           -Xms512m -Xmx1g -XX:+UseG1GC
  容器环境      用 -XX:MaxRAMPercentage=75 代替固定 -Xmx
  ```
- **原因**：`max-threads` 远大于连接池是常见的"参数看起来都合理、合起来不合理"。
  线程数是为了扛并发 I/O 等待，但**每个请求都要占一个 DB 连接**时，
  多出来的线程只是把压力从"拒绝"变成"超时"，用户体验更差。

### P2-5　图片由 Java 进程输出，建议交给 Nginx

- **现状**：`WebMvcConfig.java:79` 把 `/uploads/**` 挂成 Spring 静态资源。
- **改法**：Nginx 直接 `alias /data/campus/uploads/;`（后端仍保留该映射做兜底），并加缓存头：
  ```nginx
  location /uploads/ {
      alias /data/campus/uploads/;
      expires 30d;
      add_header Cache-Control "public, immutable";
  }
  ```
- **原因**：图片是**字节流**，走 Java 会占用 Tomcat 工作线程与 JVM 内存，
  而且现在没有缓存头，浏览器每次都要重新拉。交给 Nginx 是零代码改动的纯收益。

### P2-6　`uploads` 目录当前在源码树内 —— 覆盖部署即丢图（★ 数据安全）

- **现状**：`campus-secondhand-backend/uploads/` **存在且已有文件**（实测 2 个文件 / 0.22MB），
  且**后端目录下没有 `.gitignore`**。
- **问题**：① 用户上传的图在**源码目录里**，用"覆盖上传新版本"的方式部署会**直接丢掉**；
  ② 没有 `.gitignore` 时 `target/`（构建产物）与 `uploads/`（用户数据）都可能被提交进仓库。
- **改法**：
  1. 生产 `UPLOAD_DIR=/data/campus/uploads`（**源码树外、独立数据盘**，
     该配置项已支持环境变量覆盖 ✅，无需改代码）；
  2. 补后端 `.gitignore`：`target/`、`uploads/`、`*.log`、`.idea/`、`*.iml`；
  3. 部署脚本用"**先解到新目录再切软链**"或容器换镜像的方式，**不要原地覆盖**源码目录。
- **原因**：用户上传的图片是**不可再生的业务数据**（卖家重传一次也算骚扰）。
  它和代码放在一起，就是把数据库级别的数据放进了"可以随时被替换"的目录。

## 7.5 支付子系统上线补充（2026-09-22 新增）

> 这一节是**支付能力落地之后**新出现的部署依赖，旧清单里没有，必须并入上线检查表。
> 前两条是 P0 —— 漏掉其中任何一条，「支付」这个功能在服务器上都是**坏的，但不报错**。

### P0-11　`app.pay.public-base-url` 必须是渠道服务器能访问到的公网地址

- **默认值是空串** ⇒ 支付宝渠道 `available()` 直接返回 false ⇒ 收银台里**不显示**该渠道。
  这是**故意的失败关闭**：宁可不上线这个渠道，也不能出现「能付款、但订单永远停在待付款」。
- ★★ **变量名必须带 `APP_` 前缀：`APP_PAY_PUBLIC_BASE_URL`** ★★
  `app.pay.*` 在 `application*.yml` 里**没有任何占位符**（`resources` 下连 `pay:` 段都没有），
  只靠 Spring Boot 的 relaxed binding 从环境变量绑定：`app.pay.public-base-url` → `APP_PAY_PUBLIC_BASE_URL`
  （点、横线都换成下划线，前面加 `APP_`）。
  **少写 `APP_` 不会报任何错，只是绑不上**：值保持空 ⇒ `notify_url` 拼不出来 ⇒ 渠道消失。
  - 这一点做过**真机三场景对照**（`.workbuddy/e2e-pay-env.mjs`，判据是 `GET /pay/channels`——
    不看配置、不看日志，只看用户会看到什么）：

    | 场景 | 环境变量写法 | `/pay/channels` 实际返回 |
    |---|---|---|
    | A | 全用 `APP_PAY_*` | `["alipay_sandbox","wallet"]` ← 渠道在 |
    | B | 全用 `PAY_*` | `["demo","wallet"]` ← **渠道没了** |
    | C | 密钥用 `APP_PAY_*`，**只有回调地址**写成 `PAY_PUBLIC_BASE_URL` | `["wallet"]` ← **同样没了** |

    场景 C 就是"照着旧文档配"的下场：**只有这一个名字错，渠道就静默消失，日志里一条错都没有。**
  - 本清单与 README 里原先写的 `PAY_PUBLIC_BASE_URL` 是**错的**，已全部订正。
    同类前缀错误还有 `PAY_ENABLED_CHANNELS`（正确：`APP_PAY_ENABLED_CHANNELS`）。
  - 探针第一次跑还意外证明了另一件事：用 prod profile 起服务时
    `DeploymentGuard.requireRealDbPassword` 会拒掉 `DB_PASSWORD=123456`（护栏工作正常），
    所以那些场景是在默认 profile 下跑的 —— 环境变量绑定行为与 profile 无关，结论同样成立。
- **为什么必须是公网地址**：`notify_url` 由这个值拼出，而它是**支付宝的服务器**来访问的。
  填 `http://localhost:8080` 或 `http://127.0.0.1:8080` 时，支付宝打到的是**它自己机器上**的 8080，
  回调永远进不来 —— 而**本地日志里一条记录都不会有**（请求根本没到我们的进程），
  排查时极易被误判成「验签写错了」或「支付宝没配好」。
- **配套两条 Nginx 规则**：
  1. `/api/pay/notify/**` 必须能被反代到后端（现有 `location /api/` 已覆盖 ✅）；
  2. ★ **不得**对它加 `limit_req` —— 支付宝在收不到 `success` 时会**持续重推约 15 小时**，
     一旦被限流，重推全部落空，最终只能靠人工对账补单。
- **验收方式**（两道，先低成本后高成本）：
  1. 配好后登录调 `GET /api/pay/channels`，**`alipay_sandbox` 出现在列表里**才算名字没写错 ——
     这一步就能挡住上面那三类前缀错误，不需要真的发起支付；
  2. 再发一笔 0.01 元的沙箱单，看 `t_payment.notify_payload` 有没有落报文。
     有报文 = 回调链路通；没报文 = 前面某一环断了，且**不会有任何报错**。

### P0-12　存量库上线必须先跑 `db/upgrade-payment.sql`

- **原因**：`schema-auto.sql` 全部是 `CREATE TABLE IF NOT EXISTS`，
  对**已存在**的表会整条跳过 ⇒ **它建得出新表，但补不了旧表的列**。
  老库直接起新版本会报 `Unknown column 'balance' in 'field list'`（真机实测踩到过）。
- **顺序**：跑脚本 → **看它最后打印的「!! 待付款且已过期(下次任务会关)」这一行的数字** →
  确认能接受 → 再让应用带着定时任务起来。
  该数字 > 0 表示这批存量待付款单会在**下一个 5 分钟周期**被自动关闭。
  这是正确结果（它们早就该关了），但「我只是加了个列，订单怎么没了」必须在**事前**知道，
  而不是在验收现场才看到。
- 想给存量单宽限期：把脚本里那条 `UPDATE` 换成按 `NOW()` 回填（脚本注释里有现成写法），
  但请明确那是**宽限**而不是**修正**。

> 但「要登录」不等于安全 —— 任何一个注册过的学生账号，写一个三行的 for 循环就能把
> 这两个接口打上万次，**每一次都是一笔真实的 token 支出**。改之前全仓对这两个接口
> **一处限流都没有**，输入也没有任何长度上限。登录管的是「谁在按」，这一段管的是「能按几下」。

### 修了什么

| # | 缺陷（修复前） | 现在的做法 | 关键理由 |
|---|---|---|---|
| ① | 无长度上限 | 超长**拒绝**（业务码 1001）并提示上限值 | 不截断：静默截断会让用户拿到一段「忽略了他后半句」的 AI 结果而无从知道原因 |
| ② | 无频控 | `AiQuotaGuard`：**用户维度**（管公平）+ **全站维度**（管钱） | 费用按调用次数产生、与是谁在调无关；用户维度拦不住「注册 100 个账号各调 29 次」 |
| ③ | 输入直拼 prompt（`系统提示 + 用户问题`） | `chatModel.call(new SystemMessage(...), new UserMessage(...))` + `<user_input>` 围栏 + 输入里的围栏标签会被剥离 | 拼成一字符串时，模型没有任何依据区分「规则」与「用户正文」；只加围栏不洗输入 = 把围栏的钥匙一并交给用户 |

配置项 `app.ai-guard.*`（默认值在 `application.yml` 一处定义，生产用 `AI_GUARD_*` 环境变量覆盖）：

```
AI_GUARD_USER_MAX_CALLS=30      # 单用户在窗口内的调用上限     0 / 负数 = 不限
AI_GUARD_GLOBAL_MAX_CALLS=300   # 全站在窗口内的调用上限（★ 兜住账单的那条网）
AI_GUARD_WINDOW_SECONDS=600     # 窗口长度；配 0 会收敛到 1 秒（0 毫秒窗口 = 闸门静默失效）
AI_GUARD_MAX_TITLE_LENGTH=200   # 对齐 t_goods.title VARCHAR(200)
AI_GUARD_MAX_KEYWORDS_LENGTH=200
AI_GUARD_MAX_MESSAGE_LENGTH=200 # 对齐前端输入框 maxlength="200"
```

★ 上线前请按「可接受的月账单」反推一个 `global-max-calls`，**不要直接沿用默认 300**。

### 明确说清楚的三条边界

1. **提示注入没有被「根治」，只是被抬高成本。** 角色隔离 + 边界声明 + 围栏洗涤都是概率性的门。
   真正兜底的是「这个模型的输出只用来填充一段商品描述 / 客服话术」——
   它没有工具调用、没有数据访问权限，被绕过的后果是文案跑偏，不是泄数据。
   把定位说清楚比假装已经修好更有用。
2. **闸门是纯内存、单实例有效。** 多实例部署时每个实例各算各的，总容忍度放大 N 倍
   （与 `LoginAttemptGuard`、`InstanceSeqGenerator` 同一类边界）。要更严就把内部 `Map`
   换成 Redis `INCR` + `EXPIRE`，对外方法不用动。
3. **`quotaGuard.acquire` 必须在降级用的 `try` 之外。** 挪进去会被 `catch` 吞掉：
   AI 明明已被限流，用户拿到的却是一段看起来完全正常的模板文案，日志里也只是一条 warn
   —— 保护失效而没有任何可观测痕迹，正是本项目最怕的那一类。

## 7.7 健康检查 / 请求上下文（P1-5 + P1-6，2026-09-22 新增）

### 修了什么

| 项 | 做法 | 为什么与原文建议不同 |
|---|---|---|
| P1-5 | 自建 `GET /health`：`UP` / `DEGRADED` / `DOWN` **三态** + **限时探测** + 不回传内部细节 | ① 不引 actuator —— 它带 `/env`、`/beans` 泄露面，且健康口径与本项目「错误一律 HTTP 200」不一致，运维要记两套规则；② 两态不够 —— DEGRADED（库好、日志目录不可写）与 DOWN（库不可用）**处置动作不同** |
| P1-6 | `RequestTraceFilter`（`OncePerRequestFilter`）在**请求入口**铺 `traceId/method/uri`，`uid` 由拦截器补；traceId 沿用 `X-Request-Id` 并回写响应头；`finally` 清理；**白名单校验防日志注入** | ① 清单建议的「在拦截器里 `MDC.put`」**覆盖不到** `NoResourceFoundException` 与容器层拒绝（`preHandle` 晚于它们）；② 头部是**攻击者可控**输入，原样进日志能被 `\r\n` 伪造出整行（如假 `ERROR 支付失败`） |

### 新增配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `HEALTH_DB_TIMEOUT_MS` | `2000` | 探测数据库的**上界**；配 `0`/负数会**收敛到下限 200ms**（时限没有"无限等"这种选项） |
| `LOG_DIR` | `logs`（prod `/data/campus/logs`） | 必须与 systemd 的 `ReadWritePaths` 一致 —— 漏了日志目录时 logback **只在控制台打一行错、之后完全静默**，而 `/health` 的 `data.log.writable` 把它变成可观测 |

### 监控怎么用（★ 这三条最容易做错）

1. **判 `data.status`，不要判 HTTP 状态码** —— 端点恒返回 200（沿用前端契约），`DOWN` 也是 200 + `data.status=DOWN`；
2. 探针**不带 token**（`/health` 只放行 GET、匿名可读）⇒ Nginx 必须给它**独立的 `location = /api/health`**：
   若 `/api/` 那段加了 `limit_req`，探针会被限流拒绝，而本项目**连拒绝也是 200** ⇒
   监控看到 200 判"健康"⇒ 一条**永远常绿的假监控**；
3. 用 `allow/deny` 限内网时，别忘了把云监控的出口 IP 加进去，否则得到 403 且**后端一行日志都没有**。

## 7.9 会话凭据改 HttpOnly Cookie（D9，2026-09-23 新增）

> **原问题**：JWT 存在 `localStorage`。任何 XSS 都能一把读走，且**有效期 24 小时**——
> 读到即等于账号到手。这是「部署到公网」之后风险面变化最大的一条：
> 本地演示没人在意，上线后它就是最值钱的攻击目标。
>
> **改法**：凭据改走 **HttpOnly Cookie**（`c2c-token`），JS 读不到；同时把
> 「前端自己删 token」这条免费能力，换成**服务端清票端点** `POST /user/logout`。

### 修了什么

| 层 | 改动 | 关键点 |
|---|---|---|
| 后端 | 新增 `security/AuthCookie` | `ResponseCookie` + **HttpOnly** + **SameSite=Lax** + `Path=/` + `Max-Age` 与 `jwt.expiration` **同源派生**；`Secure` 由 `request.isSecure()` 决定（HTTP 下不加，否则"登录成功却仍是未登录"） |
| 后端 | `UserController` 登录/注册后下发 | 响应体里的 `token` 字段**原样保留**（接口契约不变），只是前端不再使用 |
| 后端 | 新增 `POST /user/logout` | 幂等、**不要求已登录**、只回一个 `Max-Age=0` 的同名同路径 Cookie |
| 后端 | `AuthInterceptor` 票据来源改为 **Cookie 优先** | 保留 `Authorization` 头作为第二条通道（探针 / Swagger / 非浏览器客户端要它） |
| 前端 | `stores/modules/user.ts` | 真实模式**不再落地凭据**；新增 `sessionHint`（不含凭据的布尔标记）作为"刷新后大概还登录着"的依据；`logout()` / `revoke()` 都通知服务端清票并清 `sessionHint` |
| 前端 | `api/request.ts` | 401 统一处理：**当场**作废本地会话（不再等用户点弹窗），原因文案取自服务端 message，"封禁"单独归类 |
| 前端 | `api/session.ts` | `readToken()` 在真实模式**恒返回空串**（凭据回流 localStorage 的闸门） |
| 前端 | `App.vue` / `AiAssistant.vue` / `utils/permission.ts` | 登录判据由 `token` 改为 `isLoggedIn`（见下面第 ② 条边界） |

### 明确说清楚的三条边界

**① Cookie 通道要求**「**同源**」，这是硬约束，不是可选优化。

- 开发：`VITE_API_BASE=/api` → Vite dev server 代理到 8080 ⇒ 同源；
- 生产：`/api` 由 Nginx 反代到 8080 ⇒ 同源。
- 同源请求浏览器**必然**携带 Cookie，且**不参与 CORS 协商**，所以后端
  `allowCredentials(false)` 保持不动是正确的（"通配来源 + 允许携带凭据"是危险组合）。
- ⚠️ **跨源部署在本项目不支持**，不是"配一下就行"。若有人把 `VITE_API_BASE`
  改成绝对地址（`http://host:8080/api`）去调试，症状是
  **「登录成功 → 立刻被弹回登录页」**（响应体里的 token 前端不再使用，Cookie 又没带上）。
  看到这个症状先查是不是跨源了，而不是去查密码。

**② 「是否登录」的判据必须是 `isLoggedIn`，不能是 `token`。**

凭据进 Cookie 之后 `store.token` 在真实模式下**恒为空串**，任何
`v-if="userStore.token"` / `if (user.token)` 都会**静默变成永远为假** ——
不报错、不抛异常，只是某个能力整体消失。本次已经在三处踩到（都是真发现，不是假设）：

| 位置 | 后果 |
|---|---|
| `App.vue` 心跳 | 一次都不发 ⇒ **全站在线状态失灵** |
| `AiAssistant.vue` 入口 | 悬浮入口永不显示 ⇒ 后端 `/ai/**` 变成**不可达的死代码** |
| `utils/permission.ts` 守卫 | 冷启动永不拉 `profile` ⇒ `isAdmin` 恒假，**管理员进自己后台被 403** |

这一类的共同点是"**没有报错、只有功能消失**"，所以补了一条**静态看守**
（`src/utils/session-credential-guard.spec.ts`）：白名单之外任何文件出现
`<store>.token` 即报红，白名单只有三个"凭据的产地与出口"（`request.ts` / `session.ts` / `user.ts`）。

## 7.10 鉴权快照缓存的真机结论与两条边界（P1-11，2026-09-23 新增）

### 为什么非要真机跑一遍

缓存这东西「看不见」：生效了接口更快，而**计时判据不可靠**（本仓纪律：次序判据 > 计时判据）。
`.workbuddy/e2e-p111.mjs` 的做法是**绕过应用直接改库**（`UPDATE t_user SET status=...`）：
应用不知道这次改动 ⇒ 不可能显式失效 ⇒ 响应码只能由缓存里的旧快照决定。
于是「改库后**立刻**仍然放行」成了一条**确定性**的「缓存存在」证据。

| 观测（同一份判据，两个产物） | 修复后 `a9b773315108` | 修复前 `cbdf3841d484` |
|---|---|---|
| 直改库封禁后**立刻**请求 `POST /user/heartbeat` | `code=0`（距改库 **28ms**） | `code=401`（距改库 **12ms**） |
| 转为 401 所需时间 | **8278ms**（TTL=10s ⇒ 兜底生效、窗口有界） | 7ms |
| 后台封禁 → **下一次**请求 | 401（显式失效立即生效） | 401 |
| 后台解封 → **下一次**请求 | 0（解封同样失效，否则缓存里留着 `banned`） | 0 |
| 改密后旧票 | 401（`token_version` +1 并被失效） | 401 |
| 合计 | **16 PASS / 0 FAIL** | **16 PASS / 0 FAIL**（能力项全"不存在"） |

> 两侧都 0 FAIL 才是「红对照成立」：同一探针在旧产物上把能力项判成 ❌，
> 而安全项（撤销链、匿名/伪造票拒绝）在**两侧都必须成立** —— 它们是防掩盖判据。

### ★ 真机逮到的第一件事：探针第一版「判据测错了对象」

第一版用 `/user/profile` 观测缓存，结果直改库后**立刻**拿到 `403 账号已被封禁`，
看起来像「缓存没生效」。回代码取证才发现 `UserService#getProfile` 里还有**第二道**封禁判定
（`userMapper.selectById` 直查库 → `forbidden("账号已被封禁")`）。
也就是说那次 403 恰恰说明「拦截器放行了、下游把它拦了」，**缓存其实生效了**。
⇒ 改用 `/user/heartbeat`（只写 `last_active_at`，**没有任何状态校验**）作为干净出口。
**报红先怀疑断言对象，别先怀疑被测实现。**

### 边界一：封禁的生效延迟取决于端点自带不带状态校验

P1-11 之后，全站对「封禁」的响应**不再是一个统一延迟**：

| 端点类型 | 例子 | 经应用封禁 | 绕过应用直接改库 |
|---|---|---|---|
| 自带服务层状态校验 | `GET /user/profile` | 立即（401） | **立即**（服务层直查库 → 403） |
| 不带校验（只靠拦截器） | `POST /user/heartbeat` | 立即（401，显式失效） | **最多慢 10 秒**（TTL 兜底） |

这**不是缺陷**，是 TTL 兜底的固有代价，且只在「有人在应用之外改了库」时才可能被观察到。
如实记在这里，免得日后有人看到 `/user/profile` 立刻 403、`/user/heartbeat` 还在 200 而怀疑缓存坏了。
顺带一个观察：同一条件下两个端点一个回 403（服务层）、一个回 401（拦截器），
前端对 401 是「清票跳登录」、对 403 是「提示无权」—— 这个差异**只**出现在这条窄窗口里。

### 边界二：缓存是进程内的

多实例部署时，**每个实例各有一份缓存**，显式失效只作用于「处理这个请求的那个实例」。
⇒ 经应用封禁后，另一台实例上该用户的缓存要等 **TTL（≤10s）** 才过期。
与本仓其它闸门同一边界。真要跨实例即时失效，得上 Redis 发布订阅 —— 与「单台云服务器」的目标不匹配，**不做**。

## 7.12 AI 多供应商降级链上线补充（P1-14，2026-09-24 新增）

> 这一节与 **§7.5（支付）** 同性质：都是「功能落地之后才出现的部署依赖」，旧清单里没有。
> ★ 与支付不同的是，**漏配这里的后果不是「功能坏掉」，而是「功能悄悄退化成模板」** ——
> 用户会以为智能客服本来就这么笨，运维也不会收到任何告警。所以它必须并入上线检查表。

### 它解决的是什么

改之前 AI 只有一条路径（`spring.ai.openai.*`，key 是占位符 `sk-placeholder`，且 `api.openai.com`
在国内网络下**连不上**）⇒ **每一次回复都是模板降级**，而日志里只有一句 `Connect timed out`。
改之后是一条**有序降级链**：`deepseek → qwen → 模板文案`（顺序由 `APP_AI_CHAIN` 决定）。
链首抛异常、**返回空串**、返回 `null` 三种情况都会自动换下一家；全失败才落回模板。
**前端零改动**（注入点仍是 `ChatModel`，装饰器对外等价）。

### 必配的环境变量（照抄）

| 配置（yml 键名） | 对应环境变量（**照抄**） | 作用 | 不配的后果 |
|---|---|---|---|
| `app.ai.deepseek.api-key` | `APP_AI_DEEPSEEK_API_KEY` | DeepSeek 应用 key（`sk-…`） | 链上少一环 |
| `app.ai.qwen.api-key` | `APP_AI_QWEN_API_KEY` | 阿里云百炼 / DashScope key | 链上少一环 |
| `app.ai.chain` | `APP_AI_CHAIN` | 链顺序，默认 `deepseek,qwen` | 用默认顺序 |
| `app.ai.deepseek.base-url` | `APP_AI_DEEPSEEK_BASE_URL` | 默认 `https://api.deepseek.com` | 一般不用改 |
| `app.ai.qwen.base-url` | `APP_AI_QWEN_BASE_URL` | 默认 `…/compatible-mode` | 一般不用改 |
| `app.ai.deepseek.model` | `APP_AI_DEEPSEEK_MODEL` | 默认 `deepseek-chat` | 一般不用改 |
| `app.ai.qwen.model` | `APP_AI_QWEN_MODEL` | 默认 `qwen-plus` | 一般不用改 |

★ **两条 key 都不配 ⇒ 链为空 ⇒ 全部回复走模板**，这是**故意的失败关闭**（与支付渠道 `available()` 同口径）：
宁可承认「AI 没接」，也不假装接了。★ 该状态在**启动日志里有明确 WARN 并点名变量名**，不再静默。

### ★★ 两个静默失效点（照抄时最容易错）★★

1. **环境变量名必须带 `APP_` 前缀。**
   `app.ai.*` 在 yml 里**没有任何占位符**，只靠 relaxed binding 从环境变量绑定。
   少写 `APP_`（例如 `AI_DEEPSEEK_API_KEY`）**不报任何错、只是绑不上** ⇒ 该供应商不注册 ⇒ 链少一环。
   这与 **§7.5 P0-11** 记录的是**同一个形态的坑**（那边是 `APP_PAY_*` 漏前缀 ⇒ 支付宝渠道静默消失）。
2. **`base-url` 末尾不要自带 `/v1`。**
   完整出站地址 = `base-url` + `completions-path`（默认 `/v1/chat/completions`）。
   把 `/v1` 写进 `base-url` 会拼出 `…/v1/v1/chat/completions`，得到**一句 404**，
   而日志里看不出「多写了一段」。★ 注意两个供应商的默认值**不一致且都对**：
   DeepSeek 写到 `api.deepseek.com` 为止，DashScope 兼容模式要写到 `/compatible-mode` 为止 —— 别「统一」它们。

### 验收方式（两道，先低成本后高成本）

1. ★ **先打观测端点 `GET /api/ai/providers`**（需要登录）：看 `available` 里有没有 `deepseek`、`qwen`。
   - `available: []` + `missing: ["deepseek","qwen"]` ⇒ **key 没配上或前缀写错**，别再往下查；
   - 响应里只报 `keyConfigured: true/false`，**绝不回显 key 本身**，可以放心贴给别人看。
2. 再发一次真实提问（如「怎么退款？」），确认回复**不是**那套模板话术。
   这两步能一次挡住上面两个静默失效点，且不需要看配置文件、不需要看日志。

### 与本清单已有条目的交叉

| 已有条目 | 与 AI 链的关系 |
|---|---|
| **L9**（AI 频控 / 长度上限 / 角色隔离） | ★ **不受影响，且必须保留**：降级发生在闸门**之后**，链上换一家不会绕过 `AiQuotaGuard`；三个供应商共用同一份频控与长度上限 |
| **P0-7**（spring-ai 里程碑版） | 本链沿用 `spring-ai-openai` **1.0.0-M6**，**没有引入新 starter**（DeepSeek 与 DashScope 都提供 OpenAI 兼容接口）⇒ 不改变 P0-7 的结论；若将来升 GA 仍需 Boot ≥ 3.4，属独立批次 |
| **D9**（HttpOnly Cookie） | `/ai/providers` 走同一套鉴权，**不新增白名单** |
| **M8**（错误一律 HTTP 200 + body 码） | ★ 链**全失败**时接口仍返回 `HTTP 200` + `code 0` + 模板文案（真机已验），**契约不变**；不要为了「暴露 AI 故障」而改成 5xx |

### 边界（如实交代，别当已闭环）

- **真实 key 从未跑过。** 三层验证（单测 11 / 全量 537 / 真机 17）打的是**本地假供应商**，
  证的是「链的行为」而非「模型答得好不好」。⇒ 上线填完 key 后**必须再验一次**（上面第 1、2 道）。
- 真实端点的「URL 形状」已单独验过：拿**故意无效的 key** 打 `api.deepseek.com` 与 DashScope 兼容模式，
  两个都返回 **401**（而非 404）⇒ 域名、路径、鉴权头位置都对，且证明当时没有代理残留干扰直连。
- `stream()` **只走链首、不降级**（流已吐出部分内容后再换家会拼出两段不同来源的话）。
  当前业务未使用流式，如实记录。
- AI key **等于计费凭据**，泄露后果与支付宝私钥同级 ⇒ 只走环境变量，仓库里绝不留真值。
