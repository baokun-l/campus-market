## 二十三、第十六轮：L10 活动 id 发号器 + 收口成全项目唯一发号器（2026-09-22，B5 批）

> 本节定位按**方法名/类名**做，不按行号。

### 23.1 起因：一次「还剩多少未修」的复核，翻出一条同族漏网

盘点存量未修项时，为了不被两份文档的 ✅/❌ 骗到，我对每一条做了**代码实证**。
其中一条是核对报告 §9.3 里躺了很久的 **B5：`ActivityService.ID_SEQ` 多实例撞号** ——
它一直被标成 `🟠 未做`，但从没进过正式批次。实测确认**它仍然存在**：

```java
// ActivityService（修复前）
private static final AtomicLong ID_SEQ = new AtomicLong();
return "act_" + Long.toString(System.currentTimeMillis(), 36)
              + Long.toString(ID_SEQ.incrementAndGet(), 36);
```

而 `t_activity.id` 是 `VARCHAR(64) NOT NULL PRIMARY KEY` —— **业务字符串主键**，
撞号 = 主键冲突 = 管理员点「新建活动」拿到一个没有任何线索的 500。

★ 这条与 **L5（订单号发号器）完全同族**：L5 在上一批已经重写，**这处漏了**。
这是本项目第三次踩到「改一处没查另一处」（前两次：单条/批量状态通道、单条/批量删除连带清理）。

### 23.2 旧实现的三个毛病

1. **纯进程内状态** —— 多实例各从 0 起，同毫秒建活动就撞号（主键冲突 → 500）；
2. **base36 两段无分隔符拼接** —— `base36(a) + base36(b)` **无法唯一切分**，
   不同的 (毫秒, 序号) 组合理论上能拼出同一个串；
3. **与订单号同族却两份实现** —— 这才是根因：一份改对了，另一份没人管。

### 23.3 ★ 改法：不只是在 ActivityService 里照抄一遍，而是**抽成全项目唯一发号器**

新增 `common/InstanceSeqGenerator`，把「毫秒 + 实例号 + 毫秒内序号」的**状态机**收成一份，
`OrderService` 与 `ActivityService` 都调它：

| | 前缀 | 形态 | 长度 |
|---|---|---|---|
| 订单号 | `""` | 17 位时间戳 + 1 位实例号 + 2 位序号 | **20**（与历史数据同形，未改） |
| 活动 id | `"act_"` | 同上 | **24**（`VARCHAR(64)` 绰绰有余） |

为什么不各写一遍：

- **「改一处必查另一处」从靠纪律变成靠结构**。发号逻辑全项目只有一份，
  就算下次又忘了扫同族，也**写不出第二份错误实现**；
- 新增的④组**结构断言**把这条钉住了：两个 Service 都**不许**再出现
  任何 `Atomic*` / `LongAdder` 字段，且**必须**持有 `InstanceSeqGenerator`。

三条刻意的取舍（沿用 L5）：

- **不依赖 Spring**：`new InstanceSeqGenerator(2)` 即可用。调用方都是 Lombok
  `@RequiredArgsConstructor` 的 Service，把它们变成需要注入的组件会改掉生成的构造器签名，
  全仓单测都要跟着补参；
- **实例号仍走 `@Value("${app.instance-id:0}")` 字段注入**（两个 Service 各持一份，
  与订单号**共用同一个配置键** —— 一个实例只需要配一次）；
- **越界实例号抛错，不静默夹紧**（夹紧会把 12 号假装成 9 号、去和真的 9 号撞号）。

### 23.4 ★★ 红绿探针打回了一条我写错的断言（本轮最有价值的一处）

第一版写的用例是「两个实例各发 300 个 id，断言两个集合**零交集**」。
红绿探针把它打回去了 —— **旧实现照样通过**。

原因很值得记：旧实现用的是 **`static`** 计数器，而同一个 JVM 里两个 Service
**共享同一个 static**，序号天然错开 ⇒ 「零交集」在单 JVM 里**永远成立**。

也就是说：**多实例撞号这个缺陷，单 JVM 的单测在原理上就观察不到**
（每个 JVM 各有一份 static，各自从 0 起 —— 差异只在跨进程时才显现）。

能真正抓住它的断言是「**实例号必须真的出现在 id 里**」：
旧实现压根没有实例号这一位，一测就露馅。改完该用例对旧实现稳定报红。

> ★ 这给红绿探针补了**第五种「撒谎」形态**：
> **断言抓不住跨进程缺陷，因为进程内静态状态把差异抹平了。**
> 判据：写「多实例」类用例时先问一句 —— **这个断言在单 JVM 里是不是也成立？**
> 如果成立，它就没在测多实例。

### 23.5 三层验证汇总

| 层 | 手段 | 结果 |

| 数据 | `verify-baseline.mjs` | 基线完好：`u=6 g=16 o=9 ol=40 ac=4`、状态 13/1/1/1、#12=pending、`AUTO_INCREMENT=17` |

真机探针覆盖的、**单测测不到**的东西：

- **Spring 上下文能不能带着 `ActivityService` 新增的 `@Value` 字段起来**（单测直接 `new`，不走容器）；
- 真实建活动拿到的 id **能不能落进 `VARCHAR(64)` 主键**、第 22 位确实是实例号、
  时间戳段确实是本次时间（±5 秒）；连建两个不撞号；
- 共用发号器后**订单号仍然是 20 位纯数字**（真机下单复验，防止重构改坏另一条链路）；
- 非 admin 建活动仍被拦（401 / 403）且**没落库**。

### 23.6 本轮踩的坑：探针自己把基线弄脏了，而「计数不变」发现不了

第一次跑真机探针，`verify-baseline` 报出状态分布变了：`on_sale:13/sold:1` → `on_sale:11/sold:3`。

原因：探针下单把最后 1 件买掉会让商品**翻成 `sold`**，收尾时我只还原了 `stock`、
**忘了还原 `status`**。而「表计数不变」这条断言**完全看不出来**（16 件还是 16 件）。

处置两条：

1. 已按种子核对（种子里只有 **#13** 本来就是 `sold`）把 #1 / #3 改回 `on_sale`，基线已复原；
2. 探针补上 `status` 一并还原，并在代码里写下这条教训。

> ★ 这是「探针自己撒谎」的第六种形态：**还原不完整，且被「聚合计数不变」掩盖**。
> 判据：还原清单要按「**下单动了几列就还原几列**」逐列核对，
> 并且收尾复核要看**分布**而不只是**总数**。

### 23.7 遗留

- **实例号只解决到「配置正确」这一层**（与 L5 同一个边界）：>10 个实例、
  或两个实例配成同一个 `app.instance-id` 仍会撞号（后者属配置错误，日志会以主键冲突暴露）。
  与本项目「单台云服务器部署」的目标不匹配，不做。
- **前端 Mock（`src/api/mock.ts:1240`）仍是旧形态**（`act_` + base36 + 进程内 `_activitySeq++`）。
  ★ 这是**核对后有意不改**：Mock 是浏览器单进程，按构造不可能有多实例，
  且 Mock 的活动 id 与后端形态本来就不同（订单号早已如此），不会掩盖真实缺陷。
  记录在此以免下次误判成"漏了"。
- `spring-ai` 里程碑版、**L9（AI 无频控 + 输入直拼 prompt）**、日志 `traceId`、
  部署 P0 六项 —— 详见 §六 未修总览。
