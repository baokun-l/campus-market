
## 附二十三、真实支付子系统：支付单 / 三渠道 / 超时关单 / 原路退回（2026-09-22）

### 23.1 起因：一次「确认支付 ¥45.00？」暴露的整条链路缺失

用户截图给的是订单中心的付款动线：点「去支付」→ 弹确认框 → 确定。
后端在这一次点击里做的唯一一件事，是把订单状态从 `pending_payment` 改成 `pending_ship`。

也就是说，「付款成功」这个判断在当时的系统里**没有任何依据**：

| 应该有的东西 | 改造前 |
| --- | --- |
| 支付渠道 | 无。用户从没选过钱从哪来 |
| 金额校验 | 无。金额只是从列表里取出来显示用的 |
| 幂等键 | 无。同一次请求重复发一百次都会成功 |
| 异步通知 | 无。没有任何第三方会告诉我们钱到了 |
| 凭证 | 无。谁付的、走哪条通道、通道流水号是什么，一个字没留 |
| 退款 | **只改状态，钱一分没动** |

前四条是「功能不完整」，最后一条是**账实不符**：界面显示「已退款 ¥45.00」，买家的钱还留在平台账上。
对账时平台记着支出 45 元，实际资金一动不动 —— 这类问题界面上看不出来，只有对账才暴露。

### 23.2 为什么是「三样全做」而不是挑一个

| 渠道 | 真实度 | 门槛 | 能证明什么 |
| --- | --- | --- | --- |
| `demo` 演示渠道 | 流程真、资金假 | 零 | 同一条链路在课堂可演示 |
| `wallet` 校园钱包 | **账真**（真扣余额、真记流水）、通道假 | 零 | 幂等、超时关单、原路退回全部可验证 |
| `alipay_sandbox` 支付宝沙箱 | **签名/验签/回调/退款全真**、资金假 | 个人实名即可 | 验签、app_id 比对、回调协议、退款幂等 |

支付宝/微信的**正式商户**要营业执照 + 对公账户 + 已备案的 HTTPS 域名，学生项目拿不到。
沙箱则是「除了钱是假的，其它全是真的」 —— 这刚好覆盖掉支付里最容易写错的那一半（协议与签名）。

★ 关键设计：**三个渠道走的是同一条建单 → 结算 → 退款路径**，换的只是末端。
所以「演示渠道跑通了」不是一条专用假路径，它对真实渠道是有意义的。

### 23.3 为什么要单独一张 `t_payment`

订单表旁边挂 `pay_time` 一列是装不下真实支付的：

- **没有凭证**：真出纠纷时平台拿不出任何第三方证据；
- **一次尝试 ≠ 一笔订单**：用户先试余额（失败）再试支付宝（成功），这两次尝试恰恰是排查支付问题最需要的东西；
- **中间态无处表达**：支付可能「已提交、结果未知」（网络断了、回调丢了），而订单状态只有「待付款 / 待发货」两个格子。

于是确立不变式：

```
一笔订单 →（0..N）张支付单，至多一张 success
订单被推进，只由「支付单成功」驱动；支付单成功，只由渠道确认
```

「至多一张 success」不靠唯一索引，靠 `status` 上的**条件更新** —— 索引管不住并发，条件更新管得住。

`t_wallet_log` 的 `amount` 是**有符号**的（支付为负、退款为正），`balance_after` 是刻意的冗余：
有了它，对账就是逐行比一个数，而不是把整张流水重新累加一遍。

### 23.4 结算的三道闸门（顺序不能调）

```
① 验签（在渠道实现里）  → 这段报文是不是渠道发的
② 支付单幂等 UPDATE ... WHERE status IN ('created','paying')  → 已经处理过就别再处理
③ 订单条件更新 markPaid WHERE status='pending_payment'        → 订单此刻确实可付
```

任何一步用「先查后写」代替，都会在并发下静默出错。

第 ③ 步不成立时（订单被超时关单抢先），**钱已经收了、货却卖不了**，此时自动原路退回。
这里有个刻意的取舍：自动退回失败时**不抛异常**（抛了会把这条支付记录一起回滚掉，钱就成了一笔"没有痕迹"的进账），
而是把原因写进 `fail_reason` 并记 ERROR 日志，留一条能被检索到的人工处理线索。

### 23.5 那个「不遵守项目约定」的接口

全项目响应一律 `{code, message, data}`，只有 `POST /pay/notify/{channel}` 返回**纯文本** `success` / `failure`。

这不是偷懒，是支付宝定的协议：它只看响应体是不是 `success` 这七个字符，不是就认为通知失败，
并按 4m / 10m / 10m / 1h / 2h / 6h / 15h 的节奏一直重推。回一段 JSON 的后果是「钱已经结算了，
但支付宝还在推同一条回调推十几个小时」。

**返回 `success` 的三种情形要分清**：

- 处理成功 → `success`；
- 渠道**明确告知交易失败**（用户取消、超时关闭）→ 也返回 `success`：我们确实收到了、也记下了，重推没意义；
- 验签失败 / 找不到支付单 / 金额不符 → 返回 `failure`：这些是**异常**，让渠道按规则重推，我们有机会在修好之后收到它，而不是永久丢掉这笔钱。

配套地，`AuthInterceptor` 里新增了 `PUBLIC_POST`（只有 `/pay/notify/**`，**仅 POST**）。
这条路径对全网开放，它的安全性完全押在验签上 —— 放开的是「能不能打到」，验签管的是「打了算不算数」。

### 23.6 超时关单：把一句口号接上真实执行路径

改造前：前端有 `ORDER_SLA_HOURS.pending_payment = 24` 用来把超时订单标红，后端 SQL 里也有 `slaBreach` 筛选片段 ——
但**全仓没有一个定时任务真的关过单**。后果是买家拍下不付款，库存被永久占住：卖家卖不了、
买家自己不解除、管理员在后台看到的只是一条普通的「待付款」。商品就这样从货架上消失了，且没有任何报错。

`PaymentTimeoutJob` 的顺序是**先关支付单、再关订单**（顺序不能反）：
支付单是「这笔钱还可能进来」的标志，先失效它，用户即便在关单瞬间付款也不会被受理。
关单本身**刻意不加 `@Transactional`** —— 每笔独立事务，否则一笔数据异常会把整批回滚，
而定时任务没有重试机制，结果是**每一轮都失败在同一笔上，后面永远处理不到**。

### 23.8 前端：「确认框」换成收银台

- 新增 `src/api/pay.ts`（渠道列表 + 状态轮询）；
- `payOrder(id, channel?)` 返回值从 `void` 变成 **`PayLaunch`**；
- 订单页「去支付」改成收银台弹窗（后端下发可用渠道，用户选一种）；
- `REDIRECT` 时把订单号存进 `sessionStorage` 再跳走，回来补查一次状态。

★ 前端**绝不能**把「接口没报错」当成「支付成功」：只有 `kind === 'DONE'`，
或轮询到 `paid === true`，才算真的付了钱。这正是改造前最大的误解。

`kind` 必须由后端显式下发 —— 前端不要写「url 非空就跳转」这种猜测，
一旦某条渠道两者都返回，猜测就会直接错。

### 23.9 ★ 真机暴露的部署级问题：`schema-auto.sql` 加不了列

启动现成的 `campus_market` 直接炸：`Unknown column 'balance' in 'field list'`。

根因：`schema-auto.sql` 是 `CREATE TABLE IF NOT EXISTS`，对**已存在的表**是彻底的空操作。
新表（`t_payment` / `t_wallet_log`）会被建出来，但给 `t_user`、`t_order` **加的列一个都不会加上**。

对策：**升级已有库必须手工跑 `db/upgrade-payment.sql`**。
它带 `information_schema` 探测、可重复执行（本次已在 `campus_market` 上跑过并验证幂等），
并诚实地把历史已付单回填成 `pay_channel='offline'` —— 那些单子当年确实没有第三方凭证，不能假装是支付宝付的。

这一条要写进上线手册：**只发新版 jar 而不跑升级脚本，等于上线即宕机**。

### 23.10 本轮踩的坑

1. mock 的 `PayChannel.code()` 未打桩 → `handleNotify` 里 `channel.code().equals(...)` NPE；
2. `new PayProperties()` 时 `@Value` 不生效 → `alipayGateway` 为 null，拼 URL 时 NPE（单测得自己塞字段）；
3. MP 单测必须 `TableInfoHelper.initTableInfo(assistant, Payment.class)`（项目既有惯例，缺了报"找不到 lambda 缓存"）；
4. 探针脚本 `spawnSync` 跑 `mvn.cmd` 必须 `shell: true`，否则 ENOENT 且**零输出** —— 脚本会把「没跑起来」谎报成「没报红」；
5. `GET /pay/notify/**` 在 **HandlerMapping 阶段**（早于拦截器）就被拒，返回 **1001 不是 401**。
   真机断言写死 401 会变成一条永远失败的断言 —— 比没有断言更糟，因为真出问题时会误以为是被拦住了。

### 23.11 遗留

- 支付宝沙箱密钥是否真去申请：不配就只跑钱包 + 演示（**沉默消失，不报错**，这是刻意的）；
- 回调公网地址（`app.pay.public-base-url`）在上云后必须显式配置，填 `localhost` 会导致「钱付了、订单永远不推进」且本地无任何报错；
- `return_url` 目前留空，用户付完停在支付宝结果页；要「付完自动跳回订单页」需配上前端地址；
- 渠道退款是**外部 HTTP 调用，不参与本地事务**。若渠道成功、本地标记失败，事务回滚会撤销订单侧而钱已经出去了 —— 窗口极小但存在，已留带支付单号的 ERROR 日志作为人工检索锚点。
