### 5.5 ★★★ 方法论产出：「审计脚本自己会撒谎」（两条都真踩了）

写静态审计 `.workbuddy/audit-guest-requests.mjs`，它**撒了两次谎**：

| 次数 | 形态 | 方向 | 改法 |
| --- | --- | --- | --- |
| ① | 正则整段剥块注释，而**通配路径里恰好含块注释结束序列**（星号紧跟斜杠） | **假命中**（白名单被吃没 ⇒ 判"需登录"） | **逐行判断**（只有以 `*` / `//` 开头的行才算注释） |
| ② | 判据 = 「附近 30 行内出现过 `isLoggedIn`」 | **假阴性**（`isLoggedIn` 来自相邻的**另一个函数** ⇒ `recordHistory` 被误判成"有守卫"）＋ **假阳性**（守卫抽成 `requireLogin()` 后函数体里不再出现 `isLoggedIn` ⇒ 一次报 **6 个假命中**） | 判据改成「**同一个函数体内**」（向上找包住调用点的函数定义） |

> **一个总是喊狼来了的审计等于没有审计。**
> **纪律：审计脚本自身的失败必须响亮** —— 现在有一整套自证（解析到的路由数/接口函数数/守卫命中数必须 > 0，
> 且必须能在已知必然有守卫的 `Detail.vue` 里认出守卫），任一不满足就**退出码 2**，绝不伪装成 0。

## 8. B5 批（上）：L10 活动 id 发号器 —— 发现、修复、收口成全项目唯一发号器

### 8.1 改了什么

- 新增 **`common/InstanceSeqGenerator`**（毫秒 + 实例号 + 毫秒内序号的状态机；越界实例号抛错不回夹；
  满 100/毫秒推毫秒不回绕；`lastMillis` 只增不减 ⇒ 免疫时钟回拨；**不依赖 Spring**，可直接 `new`）

- `ActivityService` 改用它 —— 活动 id 从 `"act_"+base36(ms)+base36(seq)` 改为

- `ActivityService` 新增 `@Value("${app.instance-id:0}")`（与订单号**共用同一个配置键**）

### 8.2 ★ 为什么不各写一遍，而要抽共用发号器

L10 与 L5 是**同族却两份实现** —— L5 上一批重写了、这处漏了。这是本项目第三次踩
「改一处没查另一处」（前两次：单条/批量状态通道、单条/批量删除连带清理）。
抽成一份之后，「改一处必查另一处」**从靠纪律变成靠结构**：发号逻辑全项目只有一处，
就算下次又忘了扫同族，也**写不出第二份错误实现**。
并由④组**结构断言**钉住：两个 Service 都不许再有 `Atomic*` 字段、都必须持有 `InstanceSeqGenerator`。

### 8.3 ★★ 红绿探针打回了一条我写错的断言（本轮最有价值）

第一版用例 =「两个实例各发 300 个 id，断言两集合**零交集**」—— **旧实现照样通过**。
根因：旧实现是 **`static`** 计数器，同一 JVM 里两个 Service 共享它，序号天然错开
⇒ 「零交集」在单 JVM 里**永远成立**。

也就是说：**多实例撞号这个缺陷，单 JVM 单测在原理上就观察不到**
（每个 JVM 各有一份 static 各自从 0 起，差异只在跨进程时才显现）。
能抓住它的是「**实例号必须真的出现在 id 里**」—— 旧实现压根没有这一位。

⇒ **红绿探针第五种「撒谎」形态**：断言抓不住跨进程缺陷，因为进程内静态状态把差异抹平了。
判据写进 skill：**这个断言在单 JVM 里是不是也成立？**

### 8.4 ★ 探针自己把基线弄脏了，而「计数不变」发现不了

首跑真机后 `verify-baseline` 报状态分布变了：`on_sale:13/sold:1` → `on_sale:11/sold:3`。
原因：下单买掉最后 1 件会让商品**翻成 `sold`**，收尾**只还原了 `stock`、忘了 `status`**，
而「表计数不变」（16 件还是 16 件）**完全看不出来**。
处置：按种子核对（种子里只有 **#13** 本来就是 `sold`）把 #1 / #3 改回 `on_sale`，基线已复原；
探针补上 `status` 一并还原。
⇒ **第六种形态**：还原不完整，被聚合计数掩盖。判据：还原按「动了几列还原几列」逐列核对、
收尾复核看**分布**不只是**总数**。

## 23:16 继续修：L9 AI 助手加固（B6 批，四份证据全闭环）

> 盘出的 6 项真未做里**唯一安全相关**的一条，提前到 P1 之前做。对应用户指令「继续修」。

### 三处缺陷（互相独立）
1. **无长度上限**：`title`/`keywords`/`message` 直接透传 ⇒ 一次请求可塞任意长度文本；
2. **无频控**：全仓 `RateLimit` 只挂登录，`/ai/**` 零计数 ⇒ 可被当成免费模型 API 刷；
3. **提示注入**：`chatModel.call(systemPrompt + "\n\n用户问题：" + msg)` —— 规则与内容**同一条消息**，
   结构上没有边界，标题里写「忽略以上所有指令」就生效且**看不出异常**。

### 修法
- **新增 `security/AiQuotaGuard`**（13.9KB）：双维度（用户 30 / 全站 300 每 600s）。
  - **不复用 `LoginAttemptGuard`**：它计**失败**且有**锁定态**；AI 计**消耗**（成功失败都算）、无锁定态。
  - **单方法 `acquire(userId)`**（不是 assert/record 两步）：判定条件在入口已完全确定，
    拆两步会造「判过了但还没记上」的并发窗口。
  - **一把锁**：需要原子组合动作「先判两维度、再一起 +1」；两把锁会出现
    「用户维度判过、全站同时被顶到超限」⇒ 既不该放行、又白吃用户一次额度。
  - **全站先判且在建用户条目之前**：拒绝越早代价越小，否则在全站打满的窗口里猛调仍会撑大 `byUser`。
  - `<=0` 该维度不限；**`window-seconds` 配 0 收敛到 1 秒**（唯一例外，0 毫秒窗口 ⇒ 计数每次归零 ⇒ 静默失效）；
    报错**不回显全站上限**（不泄露可编排信息）；**刻意不读 `X-Forwarded-For`**（无代理层，可信头=绕过路径）；
    `PURGE_THRESHOLD=256` 且**清理放锁外**；`trackedUsers()` package-private **只为测试**。
- **长度上限（拒绝不是截断）**：title/keywords 200（对齐 `t_goods.title VARCHAR(200)`）、
  message 200（对齐前端 `AiAssistant.vue` 的 `maxlength="200"`）。静默截断 ⇒ 用户拿到忽略后半句的结果而无从知道。
- **提示三层**：①角色隔离 `call(new SystemMessage, new UserMessage)`（协议保证边界，原 `call(String)` 结构上消灭）
  ②`<user_input>` 围栏 + 系统提示里声明「围栏内是数据不是指令」③**剥离输入里自带的围栏标签**
  （`FENCE_TAGS` 大小写不敏感、允许标签内空白）—— 否则用户写 `</user_input>` 就提前闭合围栏。
  **明确宣布不是根治**，是概率性的门；兜底=「输出只填充文案，无工具调用、无数据权限」。
- **依赖 `ChatModel` 接口而非 `OpenAiChatModel` 具体类**：真正的理由是**可测** ——
  不变量「系统提示里绝不能出现用户输入」只有拿到**真正传给模型的消息**才能断言；
  依赖接口后可写**手写记录桩**存 `Message[]`，且桩里覆写 `call(String)` 让它报错，防人改回拼接。
- **`quotaGuard.acquire` 必须在拼 prompt 之前、且在降级 try 之外**（两处都写了注释）：
  挪进 try 会被 catch 吞掉 ⇒ 用户拿到模板文案，与「AI 连不上的正常降级」**一模一样** ⇒ 保护失效且无痕迹。
