### ★ 顺带挖出真缺陷：`rejectRefund` 的「清空」从来没有生效

原写法 `order.setRefundAmount(null)…; orderMapper.updateById(order)` ——
**MP 默认 `FieldStrategy.NOT_NULL`，null 字段不进 SET 子句**（本项目 `application.yml` 未覆盖 `update-strategy`，已确认）。
所以订单状态退回 `pending_ship` 了，`refund_amount/reason/by/remark/time` 却原样留在行里：
`getRefund()` 判定仍成立 → 响应照样下发退款卡片；前端按 `refundTime` 统计「已退款金额」还会把它算进去。
改：单列原子 UPDATE + **显式** `set(列, null)` + `status` 乐观守卫 + 0 行受影响即报错。
（已核对 MP 3.5.6 源码：`set(col,null)` 走 `formatParam`，**没有 null 判断**会正常拼进 SET。）

### `refund.time` 语义对齐（不加库列）

前端契约里 `OrderRefund.time` 是**申请时间**、`Order.refundTime` 才是完成时间；后端一直把完成时间当 `time`。
「平台直接退」时两者同刻看不出问题，走 H1 就漏了。解法：`Order` 加
`@JsonIgnore @TableField(exist=false) refundApplyTime`，由 `fillLogs` 从 `to_status='refunding'` 那条日志回填
（与 `refundBackTarget` 用同一行数据），`getRefund().time` 优先取它。`getRefund()` 判定条件补上 `refundReason`。

### 11.5 ★★ 两个「探针自身的陷阱」（都伪装成「代码有 bug」，白排查两轮）
1. **`LAST_INSERT_ID()` 是连接级的**：每次 mysql CLI 调用都是**新连接**，「INSERT 完再单独查」拿到 **0**
   ⇒ 后续断言全打在一个不存在的主键上，**看起来完美地像「连带删除没生效」**（E5/E6 假红）。
   → 取新插入 id **必须与 INSERT 在同一条命令里完成**；断言前先证「行存在」。
2. **`POST /admin/activities/restart` 不接受 id**：服务端用 `current()` 自解析目标，
   而 `current()` 在目标被下架后会**换人** ⇒「先下架 A、再 restart、检查 A」必然失败（C5 假红）。
   → 应断言**接口返回的那条**，或先构造让解析结果必然落在同一目标的前置状态（本轮：把所有活动都压上下架标记）。
- 顺带踩到：`t_activity` 列名是 **snake_case**（`start_at`/`duration_days`），写 SQL 用了驼峰报 1054。
- **通法：探针红 ≠ 代码错 —— 先问「我断言的对象，真的是我以为的那个吗？」**
- 另一条环境坑：**沙箱会在 Bash 调用结束时杀掉子进程树** ⇒ spawn detached 后 launcher 退出 = 服务当即被杀（ECONNREFUSED）。
  正解：`run_in_background` 里跑**阻塞式** `spawnSync(java, …, {cwd: moduleDir})`（`cd` 坏了也能定工作目录）

## 12. B2 批：M4 登录失败闸门（2026-09-21 夜 续）

### 12.1 缺陷
`POST /user/login` 零次数约束。BCrypt 只抬高**单次尝试的成本**（约 100ms），**完全不限次数** ⇒ 弱口令必被撞开。

### 12.2 实现
- 新增包 `security` + `LoginAttemptGuard`（`ConcurrentHashMap`，**两个独立维度**）：
  账号 5 次/15 分钟 → 锁 15 分钟；来源 IP 100 次/15 分钟 → 锁 5 分钟。
- ★ 不按清单原提案的「用户名+IP 合成 key」：撞库时每个账号只错一次，合成 key 各自都到不了阈值 ⇒ **拦不住**。
- ★ IP 维度「**松阈值 + 短锁定**」：假阳性代价是「整栋楼登不上」（NAT/反代共用一个公网地址）
  ⇒ 分工：**账号维度负责拦人，IP 维度只负责拦脚本**。
- ★ 不引 Redis（单实例足够；多实例边界 = 各实例各算各的，与 L5 同类；将来把内部 `Map` 换成 Redis `INCR`+`EXPIRE` 即可，对外方法不动）。
- ★ **不采信 `X-Forwarded-For`**（客户端可伪造，采信=没装，且给人「已防住」的错觉）→ 用 `getRemoteAddr()`；
  反代部署需开 forward-headers + 显式声明受信代理（属部署项，不写进代码猜）。
- `UserService.login(username, password, clientIp)` 四步**顺序不能调**：
  `assertNotLocked`（**查库之前**）→ 口令错 `onFailure`（**用户不存在也计数**）→ 状态闸门（**封禁不计数**）→ `onSuccess`（**只清账号、不清 IP**）。
- 第 5 次失败**仍返回「用户名或密码错误」**（锁定提示第 6 次才出现）；用户名 **trim+小写**归一化；
  内存按水位惰性清理，谓词必须「**锁已到期 且 窗口已滑过**」（只写「已到期」会把仍在锁定中的有效条目清掉 = 开天窗）。
- `application.yml` 新增 `app.login-guard.*`（5 个键全部可环境变量覆盖）；`ip-max-fails` 调成天文数字即可近似关闭辅网。
- 前端**零改动**：`request.ts:125` 对非 401/403 的响应统一 `ElMessage.error(res.message)`，锁定文案走既有 **1001** 通道
  ⇒ **本次不需双副本回流**；`sync-check.mjs` 复核两副本仍 **0 差异**。

### 13.2 四个关键决策（都写进代码注释了）

1. **判据用 `create_time`，不用设计稿写的 `update_time`** —— `update_time` 是

3. **单列 UPDATE**（`snapshot-write-audit` 判据一问）：`t_goods` 的

### 13.3 ★★ 本轮最大的收获：红绿抓到一条「永远为真」的断言

RED-A（把 `.set` 与 `.eq` 的状态值**对调**，实现变成「把已下架的商品重新上架」）
**第一次跑是绿的**。因为最初断言写成「参数里同时含 `off_shelf` 和 `on_sale`」——
两个值对调后**照样成立**。改成「按 SQL 段取占位符实参」才真正变红：

```java
argsInOrder(w, sqlSet(w))    // 必须恰为 [off_shelf]
argsInOrder(w, sqlWhere(w))  // 第 1 个是 on_sale，第 2 个是 LocalDateTime
```
（实现：正则抽 `#{ew.paramNameValuePairs.MPGENVALx}` 末段作 key 查 `getParamNameValuePairs()`；
注意 `getSqlSet()` 只求 SET 段、`getSqlSegment()` 才触发 WHERE 段惰性求值。）

**纪律：只跑「绿」发现不了这种用例。凡是写完断言，都要问「把实现改坏了它会不会红」。**

### 13.4 ★★ 手工入口 ≠ 定时触发（单独写探针的理由）

### 13.5 ★ Windows 坑：`mysql -e "多行 SQL"` 会被换行截断

**都没有专门的 `@ExceptionHandler`** → 落到兜底分支 → 500「服务器内部错误」。

  命中率陡增 —— 而「文档里明明有那个接口」会让 500 显得更像后端挂了。
