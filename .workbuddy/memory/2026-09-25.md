## 四、本轮新踩的三个坑（都不是业务代码问题，是**生成 PDF 的工具链**问题）

### 4.1 `Page.printToPDF` 会**真正挂死**，根因是「打印路径要缩放大图」

- 现象：同一份 HTML，13 张 **1440px PNG（合计 3.7MB）** 时 `printToPDF` 10 分钟不返回；
  把 `<img>` 全换成等高等宽占位块后，**9.4 秒**完成。
- ⇒ 结论：卡的不是 CSS / 分页 / 文档长度（31654px、23 张表、13 个 h2 都没事），**只是图片缩放**。
- 修法：把截图**降到印刷所需宽度再嵌**。A4 正文宽 ≈ 674 CSS px，取 **880px** 留一倍冗余，
  JPEG q=0.82 → **3.72MB → 0.72MB**，随后 8.7 秒出 PDF。
- ★ 仍要配 `figure img { max-width:100%; height:auto }`，让布局确定，别依赖「浏览器自己缩」。

### 4.2 无头 Chrome 会「等固定超时」——先清**代理环境变量**与**残留进程**

- 现象：一份**一页纯文本**的探针 HTML 也要 **精确 5 分 03 秒**（两次跑一分钟不差）⇒ 典型的「等超时」而非「算得慢」。
- 本机背景：系统代理指向 **未运行**的本地端口（Nano 65532），WorkBuddy 会给子进程注入
  `HTTP_PROXY/HTTPS_PROXY`；Chrome 的后台请求（组件更新 / variations / safe browsing）会在上面长时间重试。
- 修法（`html2pdf-*.cjs` 里已固化）：spawn 时**删掉所有 `*_PROXY` 环境变量** + `NO_PROXY=*`
  + `--proxy-server=direct://` + `--proxy-bypass-list=*` + `--disable-background-networking`
  + `--disable-component-update` + `--disable-sync` + `--no-service-autorun`。
- ★★ **另一个更隐蔽的元凶是「上一次超时留下的 Chrome 进程」**：它仍占着 `--user-data-dir`
  与调试端口，新的 Chrome 起来后行为异常（同样表现为等超时）。
  ⇒ **每次跑之前 `rm -rf` 掉 profile 目录**，并确认没有残留 chrome 进程；清干净后同一份文档 3.0 秒完成。

### 4.3 停在 `about:blank` 时**加载不了 `file://` 图片**

- 用 canvas 缩图时报 `img.onerror → "load fail"`，看不出是来源问题。
- 原因：`about:blank` 是不透明来源，`file://` 的 `<img>` 被安全策略拒绝。
- ⇒ **先把页面导航到一个 `file://` 目录**（如 assets/ 的目录列表页），再加载同源图片；
  并保留 `--allow-file-access-from-files`。

### 4.4 顺带确认的写法

- 导出 PDF 用 **CDP `Page.printToPDF`**，**不要**用命令行 `chrome --headless --print-to-pdf`：
  后者 `printBackground` 默认关，报告里深蓝章节条、三色提示框、斑马纹表格会**全部消失**。
- 参数：`printBackground:true` + `preferCSSPageSize:true` + `paperWidth/Height: 8.27/11.69` + 四边 margin 0（页边距交给 CSS `@page`）。
- 校验 PDF 的**结构自证**（不依赖阅读器）：`/Count` 取最大值 = 页数、`/Subtype /Image` 计数 = 内嵌图数、
  `/FontFile2|3` 计数 > 0 = 中文字体已内嵌、`/MediaBox` ≈ `594.96 x 841.92` = A4、末尾 `%%EOF`。
- 没有可脚本化的 PDF 阅读器时，**用「打印媒体 + A4 宽度 794px + 按页 clip」逐页截图**来预览 PDF 的实际分页。
