## 诊断：发布商品报 500「服务器内部错误」

### 根因（铁证，探针复现）
**前端把上传图片压成 base64 data URL 直接塞进商品字段，数据库列宽装不下。**

`Publish.vue:512` → `compressImageToDataUrl(f.raw, maxDim=1200, quality=0.82)`（`utils/image.ts`）
→ 输出 base64 约 **100~400KB**，然后 `cover: dataUrls[0]`、`images: dataUrls.filter(Boolean)` 直发后端。

| 探针用例 | 结果 |
|---|---|
| `cover` = 3KB data URL | **500**（`cover` 是 `varchar(255)`，任何 data URL 必超长） |
| `cover` = `/goods/cat1-1.jpg` | OK（对照） |
| `images` = [3KB] / [40KB] | OK |
| `images` = [80KB] | **500**（`images` 是 `text`，上限 64KB） |

→ **只要卖家选了商品图，发布 100% 失败**；不选图才能成功。这解释了「有时能发、有时报错」。

### 附带发现：`publishGoods` 零参数校验（= 清单 H3）
同批探针还测出 5 类输入直接 500（都是 DB 约束当校验器）：

| 输入 | 结果 | 违反的约束 |
|---|---|---|
| title 缺失/空 | 500 | `title` NOT NULL |
| title 超长(260) | 500 | `title` varchar(200) |
| price 缺失 | 500 | `price` NOT NULL |
| location 超长(260) | 500 | `location` varchar(200) |
| price 超大(9999999999) | 500 | `price` decimal(10,2) |

且**应拒绝却通过了**：`price=0`、`price=-5`（负价格！）、`categoryId` 缺失（幽灵商品）、`deliveryMethod='teleport'`（幽灵状态）。

## 同类缺陷全盘排查：「还有没有其他类似的问题」

用户提问：检查是否还有同类「层与层隐含假设不一致 / 窄列撑爆 / 数据库约束当校验器」的缺陷。

### 结论：实测 23 处同类缺陷，全部收敛为 1001
`publishGoods` 那 5 类是**症状不是病根**。真正的病根是：**全项目 Service 层普遍缺失边界校验，把 MySQL 列宽 / NOT NULL / 枚举当成了校验器**。
在 MySQL `STRICT_TRANS_TABLES` 下，超长 / 缺失 → **报错而非静默截断** → 被 `GlobalExceptionHandler` 兜底成 code=500。

### 核心产物：`common/Validators.java`（新增，统一边界校验）
一个工具类供 9 个 Service 复用，避免各写一套。常量 `TEXT=2000`；方法：
`required(value,max,label)` / `optional(value,max,label)` / `range(Integer,min,max,label)` / `range(BigDecimal,min,max,label)` / `oneOf(value,allowed,label)` / `phone(value,label)`。
**上限口径与 schema.sql 列宽逐条对齐**（varchar(n)→n，TEXT→TEXT）；非法值统一抛 `BusinessException.paramError`（**1001**）。
提示语自带实测值，如「商品标题最多 200 个字（当前 260）」。

### ★ 过程更正（审计员的错误结论，已推翻）

「`pageSize>500` 时 `LIMIT` 截到 500 但 **OFFSET 仍按原值算 → 静默跳行**」——**不成立**。
MyBatis-Plus 的 `handlerLimit` 是**先把 `page.size` 改成 500**，之后才由该 size 计算 OFFSET，翻页连续不跳行。
真实问题只是**回显值**（= D10）。**教训：子代理的推导必须复核，尤其"并发/分页"这类看不见的行为。**
