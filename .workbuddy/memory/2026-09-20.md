### 7. 22:00 追加：核查「显示在线状态」开关控制的是什么（用户提问）

问题：设置页那个「显示在线状态」到底控制哪里？为什么首页看不到任何在线/隐匿状态？

代码事实（**纯前端展示层，完全不涉及后端**）：

- 判定函数 `src/utils/prefs.ts#isUserOnline(id)`：`((id*7 + floor(Date.now()/86400000)) % 10) < 6` —— 用户 id + 当日天数做确定性散列，**约六成用户「在线」、当天不闪烁、次日可能变**；函数注释里自己写明是「伪在线」（真实在线名单需要后端心跳/WebSocket，本项目没有这一层）
- 开关 `appStore.settings.showOnline`（`stores/modules/app.ts`，默认 `true`），`updateSetting()` 只改 Pinia 值，靠 `persist.paths` 落到 localStorage `c2c-app` —— **只影响本机/本浏览器，不写后端、不跟账号走**
- 全站**只有两处**渲染在线标识：
  1. `views/message/Index.vue:66` —— 会话列表头像右下角绿点（`v-if="showOnline && isUserOnline(s.peerId)"`）
  2. `views/goods/Detail.vue:81` —— 商品详情页卖家徽标（`{{ sellerOnline ? '在线' : '离线' }}`，绿/灰两态）
- ★ 语义坑：开关名叫「显示**我的**在线状态」，实现却是「**给不给我看别人**的在线标识」。判定在**观看者自己的浏览器**本地用同一算法算 → 关掉开关**不会让别人看不到你**，只让你自己看不到那些绿点。答辩若被追问这点要能说清
- 为什么首页毫无变化：`views/Home.vue` 根本不渲染卖家信息（grep `卖家/avatar/seller` 零命中），首页卡片是纯商品卡；没有承载标识的 UI，自然没有可被隐匿的东西。要看到开关效果必须去**消息页**或**商品详情页**

#### 8.2 四个关键决策（每个都是「不这样做就是个新坑」）

1. **时间戳 + 时间窗，不用布尔列 `is_online`**：布尔列的僵尸在线要定时任务清（任务周期=状态误差，任务挂=全站永久在线），且区分不出「30 秒前刚走」和「三天没来」。现在状态是**算出来的**不是**维护出来的**。
2. **心跳无参**：活跃时刻由服务端时钟定。允许客户端上报时间戳 → 改本机时间就能刷在线。
3. **隐私开关只改 `show_online`，绝不碰 `last_active_at`**：关展示 ≠ 伪造离线 ≠ 清空活跃记录。探针专门钉了这条（关闭后时间戳逐字节不变）。
4. **`PATCH /user/privacy` 只认 Boolean 字面量**：`"false"` 走 `Boolean.parseBoolean` 会静默当 false —— 用户以为只是「关掉展示」，实际是被拼错的参数关掉的。非布尔直接 1001。

### 9.2 ★ 揪出一个真实缺陷：演示脚本硬编码 `USE campus_market;` → 跨库泄漏

被探针的「清理后真实库与基线一致」断言抓出来的：场景 C 明明打的是 `campus_market_demotest`，结果那个库 `g=0`，而真实库 `campus_market` 被改了（商品 17→16、分类 11→9、地址 15→9）。

根因：三个演示脚本第 13～23 行都有 `USE campus_market;`
- 人工执行时**无害**（命令行已给库名，`USE` 是废话）
- 交给 Spring 自动执行时是**地雷**：连接被无声切回 `campus_market`，**数据灌进别的库、目标库依旧空，且一句错都不报**

修法：4 处 `USE` 全删；脚本只操作「调用方选定的那个库」（人工靠命令行参数，自动靠 `spring.datasource.url`）。并补**静态防线**：探针每次先扫这 5 个自动初始化脚本，命中 `USE`/`CREATE DATABASE` 即判红。

顺带好消息：真实库被重置到的那组数字恰好就是文档一直用的**基线**（`u=6/g=16/o=9/ol=32/al=9/ac=4`，状态 13/1/1/1）。漂移掉的只是探针残留的 1 商品 + 2 分类 + 6 地址，业务数据一行没丢。

### 9.3 四条硬约束（不这样做就是新坑）

1. **不能把 `schema.sql` 直接配到 `schema-locations`** —— 它是重建型（17 个 `DROP TABLE IF EXISTS`），配上去等于每次启动清空全库
2. **自动执行的脚本绝不能出现 `USE` / `CREATE DATABASE`**（见 9.2）
3. **`data-locations` 是整体覆盖、不跨来源合并** —— `application-demo.yml` 必须把 `seed-base.sql` 再列一遍，否则 demo 环境下用户表为空、**谁都登不进来且日志无错**
4. **`createDatabaseIfNotExist=true` 不能省** —— 否则卡在「库不存在 → DataSource 连不上 → 脚本没机会跑」，表现为「自动建表没生效」，日志里只有一句 `unknown database`

  - A2 重启：种子不重复灌（用户仍 6 / 分类仍 9 / 设置仍 1 / 公告仍 2）

### 9.5 探针自身的两个坑（下次直接用）

1. **`ScriptUtils` 只在 DEBUG 级别打印脚本名**（`Executing/Executed SQL script from class path resource [db/xxx.sql]`）。默认级别下这几行**根本不存在** → 初版探针据此断言得到 4 个假 FAIL。启动参数固定带 `--logging.level.org.springframework.jdbc.datasource.init=DEBUG`
2. **日志里的中文是乱码**（JDK 17 在 Windows 按 GBK 写管道）→ grep 中文（如「基础种子复核」）**注定失败**，证据锚点一律用 ASCII

### 9.6 教训

- **「自动化」的价值不只是省命令**，而是把「顺序敏感 + 漏跑不报错」这类**静默失败**变成不可能。本轮救回的两个静默失败（跨库泄漏、`data-locations` 覆盖）靠的都是同一件事：**让后果可见**（探针比对 + 日志取证）。
- **同一份脚本被两种方式执行时，「两边都成立」比「在一边能跑」重要得多**。一句 `USE` 在命令行下是废话，在 JDBC 下是跨库写 —— 语句正确性依赖调用方式，就是个坑。
- **写校验逻辑要防「校验自己空转」**：生成器初版正则只取「第一个分号之前」，而 `t_user` 有两条 INSERT，后 3 个用户根本没被校验却报 PASS。现改为「取全部 INSERT 片段」+「一条都没提取到就判 BROKEN」。
