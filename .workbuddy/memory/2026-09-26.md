## 二、结论（决策已定，别再重新推导）

**能装下，但余量只有 7%，实际会不稳。项目自己文档定的参考规格就是 2核4G。**

| 2核4G · 照搬现有参数 | 1895 MB | 2201 MB（54%） | ✅✅ 项目设计目标 |

★ **短板只在内存，不在 CPU。** `TOMCAT_MAX_THREADS=50` / `DB_POOL_MAX=10` 正是按 2 核取的
（部署清单 P1-12：「2核取 8~10」）。**2 核是够的。**

## 五、本次踩到的工具坑（下次直接用正确姿势）

1. **`wmic.exe` 被安全策略拉黑**（Program Blacklist），不可绕过 ⇒ 用 PowerShell/Node 取系统信息。
2. **PowerShell 工具在本会话不回显输出**（`exit code 0` 但 stdout 空，连写文件也没落地）
   ⇒ 改用 Node / Bash 采集。
3. **`tasklist` 的内存列本机不可信**：`mysqld.exe` 报 **3,116 K（3 MB）**，对服务型进程明显错
   ⇒ 量 JVM 用 `jcmd VM.native_memory`，量 MySQL 用 `performance_schema`，**不要用 tasklist**。
4. **Node `execSync`/`spawnSync` 起子进程被沙箱拦**（`EBUSY`，连 `cmd.exe` 都起不来）
   ⇒ 用 `execFileSync` 直接给 exe，或干脆在 Bash 里跑。
5. **Git Bash 会把 `/FI`、`/FO` 当路径改写**（报 `无效参数 'C:/.../FI'`）
   ⇒ 前置 `MSYS_NO_PATHCONV=1`。
6. 脚本里**切了目录之后**再用相对路径必然失效 ⇒ LOG/OUT 一律绝对路径（`ROOT="$(pwd)"` 先算）。
7. Bash 里 `java ... &` 起的进程会随**本轮工具调用结束**被回收 ⇒ 想测启动后的状态，
   必须**在同一条命令内**完成「起 → 等 → 测 → 杀」。

## 六、与规格无关、但会挡住上线的四件事

1. **备案**：大陆轻量服务器，域名走 80/443 必须 ICP 备案。

   **正式支付宝要求 https 域名** ⇒ 没备案只能演示「浏览/发布/下单/钱包支付」，
   支付宝沙箱回调还得继续靠 cpolar 隧道（或 IP+非标端口，沙箱或许可行）。
2. **首次建库**：prod 默认 `spring.sql.init.mode=never`，要**手工跑一次** `db/schema.sql`
   （DROP+CREATE 重建型，仅限空库）。★ **绝不能灌 `db/seed-base.sql`**——内含公开弱口令 `admin/admin123`。
3. **`APP_` 前缀**：AI 与支付的所有 key 少写 `APP_` **不报错、静默失效**。

   `GET /api/pay/channels`（应见 `alipay_sandbox`）验收。
4. **`demo` profile 是资损后门**（`DELETE` 四表后重灌）⇒ systemd 里已写死 `prod`，打包已排除 `demo-*.sql`。

## 七、若真买 2核2G 的必做清单

### 8.1 ★ 纠正：我上一条对「无固定流量」的担心是**错的**

我原本提示「可能按流量计费、被刷会失控」。**经阿里云官方文档核实，恰好相反**：

> 「如果套餐中显示 **无固定流量**，则表示流量可无限使用，**不会产生超额流量**」
> 「此类套餐不设每月流量配额上限；无论出网流量使用多少，均不计费」
> 控制台「服务器概览」里**没有**「流量」监控指标即属此类。（来源：阿里云帮助中心《计费项》《计费常见问题》）

⇒ **流量这一项完全不是风险，反而是优点**（200Mbps 峰值 + 流量不计费，演示很友好）。
★ 教训：涉及第三方产品的计费口径**必须查官方文档**，不要凭常识推断。

### 8.2 ★★ 镜像选错了：宝塔面板与本项目不匹配

**本项目零 PHP 依赖**（已 grep 全仓 `*.xml/*.json/*.yml/*.conf/*.md`，无 `.php`/`php-fpm`/`composer` 命中）。
而 `deploy/nginx-campus-market.conf` 用的是**标准 Debian/Ubuntu 路径**：

- `/etc/nginx/sites-available/`、`/etc/nginx/snippets/campus-proxy-headers.conf`
- `/etc/letsencrypt/live/your-domain.com/{fullchain,privkey}.pem`
- 静态根 `/var/www/campus-market`、上传别名 `/data/campus/uploads/`

宝塔那套是 `/www/server/nginx/` + `/www/server/panel/vhost/nginx/` ⇒ **项目的 conf 直接 `cp` 过去不生效**。
且宝塔会引导装 LNMP，**PHP-FPM 纯属白占内存**；面板自身 Python 常驻还要 ~100-150 MB；
另外它默认开 8888 面板端口 = 多一个公网暴露面。

⇒ **买「系统镜像」（Ubuntu 22.04 / Alibaba Cloud Linux），手装 JDK 17 + Nginx + MySQL 8**，
与 `deploy/` 三件套严格对应。这也正是本项目原本的设计假设。

### 8.4 仍无法绕过的一条：备案

`nginx-campus-market.conf` 的设计本就是「域名 + HTTPS + Let's Encrypt」：
`server_name your-domain.com`、80 端口做 ACME 校验、443 上 `ssl_certificate`。
而**上海（大陆）节点域名走 80/443 必须 ICP 备案**（阿里云提供备案助手，通常 1~2 周）。
未备案的临时打法：直接用 `IP:非标端口` 暴露后端（但会丢掉 Nginx 的登录限流 / TLS / 静态缓存），
支付宝沙箱回调继续走 cpolar 隧道。彻底不想备案则只能选**中国香港等境外地域**（延迟高，且正式支付仍要 https 域名）。

| --- | --- | --- |
| Total committed（空载真实占用） | **712,111 KB ≈ 696 MB** | **439,308 KB ≈ 429 MB**（首次读数 477,897 KB） |

## 九、2核2G 的调优方案与影响评估（20:55）

爸爸要求：**不改项目**，只给调优参数 + 说明对项目的影响。

### 9.1 ★★ 先更正上一轮的一个数字

上一轮说调优后整机 **1285 MB**，那是按 MySQL ≈300 MB 估的，**漏算了「缓冲池从 8M 升到 128M 要多花 120MB」**。
修正：MySQL 调优后 ≈ **345 MB**（400 −170 关 perf_schema +120 升缓冲池），
⇒ 整机调优后 = 679 + 345 + 20 + 275 = **1319 MB，余 729 MB（36%）**。方向不变，但要留底。

### 9.2 代码里核对出的、决定影响面的事实（都经 grep/open 验证）

| 事实 | 证据 | 对调优的意义 |
| --- | --- | --- |
| 分页有硬顶 500 条 | `common/PageResult.MAX_PAGE_SIZE = 500`，`MybatisPlusConfig` 的 `MaxLimit` 读同一常量 | 列表接口不会因 `pageSize` 大而爆堆 |
| **服务端不做图片解码** | 全仓 `grep ImageIO\|BufferedImage` 只命中 `AlipayRsa2.java` 的 RSA 签名（Base64 小串） | **上传图片只落盘，不吃堆** ⇒ 2MB 图 × 并发不按倍数放大 |
| **3 个定时任务** | `GoodsOfflineJob` `0 30 3 * * ?`（每天）、`PaymentReconcileJob` `0 */2 * * * ?`（**每 2 分钟**）、`PaymentTimeoutJob` `0 */5 * * * ?`（每 5 分钟） | 对账任务是该项目**最频繁的内存活动源**，且内含外部渠道 HTTP 调用 |
| **存在未分页 `selectList`** | `ActivityService:421`（全部活动）· `AnalyticsService:111`（已支付订单统计）· `PaymentService:607/714/720`（对账三个查询）· `UserService:893`（某用户全部浏览历史）· `NoticeService:40` · `OrderService:1184` · `UserService:405/716/736/904` | **随数据量线性增长** ⇒ 数据涨到十万级时先炸的是这些，不是堆大小 |
| `-XX:+ExitOnOutOfMemoryError` 已配 | `deploy/campus-market.service:42` | 堆满 = **进程直接退出**（不降级），systemd `Restart=on-failure` 5s 后重启 |

### 9.3 调优清单（服务器侧，不动仓库代码）

**JVM**（`deploy/campus-market.service` 的 `ExecStart`）：`-Xms512m -Xmx1g` → `-Xms256m -Xmx512m`；
可选加 `-XX:MaxMetaspaceSize=160m`（实测 Metaspace 用 56MB，3 倍余量）与 `-XX:+HeapDumpOnOutOfMemoryError`。

**MySQL**（`/etc/mysql/mysql.conf.d/mysqld.cnf`）：
```ini
performance_schema = OFF          # 实测内部内存 329.5MB，关掉省约 170MB —— 最大一笔
innodb_buffer_pool_size = 128M    # ★ 本机是 8M，这一项是「往上调」，会多花 120MB
max_connections = 50              # Hikari 只开 10 条，151 纯属浪费
slow_query_log = ON               # 关掉 perf_schema 后的替代排查手段
long_query_time = 1
```
★ **不要动 `innodb_flush_log_at_trx_commit`** —— 它压根不是内存优化项，
改了只换来「崩溃丢最近 1 秒事务」，而本项目有支付模块，纯属无谓冒险。

**系统**：2GB swap（`swapon` + 写 `/etc/fstab`）＋ `vm.swappiness=10`；可选关 `snapd`/`cloud-init`。

**部署纪律**：★ **不在服务器上构建**（前端 `vite build` 峰值 >1GB，直接 OOM）—— 项目本来就是这个策略。

### 9.4 ★★ 最容易被忽略的坑：覆盖式部署会冲掉手改

仓库里 unit 写的是 `-Xms512m -Xmx1g`。在服务器上改成 512m 后，
**下次覆盖式部署重新 `cp deploy/campus-market.service` 就退回 1g**，然后某天又开始 OOM。
⇒ 要么把**仓库那份也改掉**（但爸爸说了不改项目，那就）在服务器上**另存一份不被覆盖的 unit / drop-in override**
（`/etc/systemd/system/campus-market.service.d/override.conf`，systemd 原生支持，覆盖式部署不会碰它）。
★ 这与项目文档里「覆盖式部署会把历史日志一起删掉」是同一族问题：**手工改动必须放在部署覆盖面上**。

### 9.5 修正后的最终预算

| 组件 | 照搬现有 | 调优后 |
| --- | --- | --- |
| JVM 峰值 | 1202 | **679** |
| MySQL | ~400 | **~345** |
| Nginx | 20 | 20 |
| 系统/OS | 275 | 275 |
| **合计** | **1897** | **1319** |
| **余量 / 2048** | **151 (7%)** ⚠️ | **729 (36%)** ✅ |

★ 判定口径：JVM 是**实测**（`jcmd`），MySQL 是**估算**（唯一实测锚点是内部内存 329.5MB），
Nginx/OS 是经验值 —— 回复里必须区分，不能把估算讲成实测。

## 十、要不要买域名（21:05）

### 10.1 项目对域名的真实依赖（已核对）

- **前端零域名依赖**：`.env.production` 用 `VITE_API_BASE=/api`（相对路径）+ `VITE_BASE=/`
  ⇒ 换成 IP 访问**前端不用改、不用重新构建**。
- 唯一的强依赖是 `deploy/nginx-campus-market.conf`：写死 `server_name your-domain.com;`、
  443 上 `ssl_certificate /etc/letsencrypt/live/your-domain.com/...`、80 端口 `return 301 https://`。
  用 IP 方案时这一份要在服务器上改（`server_name _;` + 只留 80 + 去掉 301 与 ssl）。**仓库不用动。**
- `APP_PAY_PUBLIC_BASE_URL` 见下。

### 10.2 ★★ 更正：「要 https 就必须有域名」现在是**错的**

我上一轮这么说过。核实后：**Let's Encrypt 自 2026-01-15 起 IP 地址证书已 GA**
（官方博客《6-day and IP Address Certificates are Generally Available》）。

但有三个限制，决定它**对课程项目不实用**：
1. IP 证书**必须走 `shortlived` profile**，有效期仅 **160 小时（6 天）** ⇒ 必须全自动续期
2. Certbot（5.4+，`--ip-address`）目前**只能签发、不能自动装进 web server** ⇒ 要手工配
   `ssl_certificate` 指向 `/etc/letsencrypt/live/<ip>/fullchain.pem` + 写 `--deploy-hook`
3. nginx / apache 插件**尚不支持** IP 证书（只能用 webroot / manual / standalone）
⇒ 能做，但 6 天一续 + 手工配置，对演示项目是"能做但没必要"。

### 10.3 支付宝回调对地址的要求（查了官方支持中心）

支付宝官方 FAQ（opensupport.alipay.com）原文：
> 「确保异步通知面地址(请求参数 notify_url)的路径前面加上 http:// 或https://。例:https://您的域名/notify_url.php，
> **支持 ip 地址方式**。（推荐使用域名）」
> 「不能以 `http://localhost` 开头，必须外网域名可访问」

⇒ 官方口径是 **http/https 都认、支持 IP**。沙箱环境校验比生产宽松（多方来源一致）。
但**生产/正式收款**实践中普遍要求 HTTPS 域名。
另注：官方明确**不支持自签名证书**（若有证书，只认官方 CA 签发的）。

### 10.4 备案与域名是两件事

- **备案绑定的是「域名 + 大陆服务器」的组合**。**纯 IP 访问不需要备案** ⇒ 不买域名 = 不用备案 = 立刻能上线。
- 买了域名要连带：实名认证 → ICP 备案（1~2 周，需身份证 + 手机核验）→ 域名解析。
- ★ **备案要跟着服务器厂商走**（服务器在阿里云就在阿里云备案最省事，跨厂商要加"接入备案"）。

### 10.5 结论（给爸爸的建议）

| | 不买域名（IP 直连） | 买域名 |
| --- | --- | --- |
| 成本 | 0 | `.com` 首年 ¥30~60 / `.cn` ¥20~30（常有 ¥1 首年） |
| 等待 | 立即可用 | 备案 1~2 周 |
| HTTPS | 无（或 6 天一续的 IP 证书，不推荐） | ✅ Let's Encrypt 免费 |
| 支付宝沙箱 | ✅ 官方支持 IP | ✅ |
| 正式支付宝收款 | ❌ | ✅ |
| 备案 | 不需要 | **必须**（走 80/443） |
| 演示观感 | 给老师看 IP | 体面 |

⇒ **先用 IP 跑通（0 成本 0 等待）；答辩在两周内就别等备案**；域名 + 备案当后续加分项。
